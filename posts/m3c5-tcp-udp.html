模块三第 5 章：TCP 与 UDP

计算机网络2026-11-25 · 模块三

IP 只管把包送到地方，送丢了、送乱了、送重了，它一概不管。网页打开一半卡住、文件下载到 99% 失败、视频通话一卡一卡——这些问题都发生在 IP 之上的一层：传输层。这一章讲传输层的两个主角：TCP 和 UDP。一个负责“稳稳送到”，一个负责“尽快送到”。学安全的人必须先分清它俩，因为后面几乎所有攻击和排错——端口扫描、会话劫持、SYN 泛洪、DNS 欺骗——都是在这两个协议的地盘上发生的。

为什么需要两种传输协议

网络上的数据有两种脾气。一种是“一个字节都不能错”：网页、文件、邮件、登录密码，错一个字节就全毁了。另一种是“宁可丢一点，也不能等”：语音、视频通话、游戏，你说的一句话晚到半秒就没意义了，但丢一两个音节还能听懂。一种协议伺候不了两种脾气，于是有了两个：TCP 给第一种，UDP 给第二种。记住这个分工，后面所有选择题都有答案：要可靠，选 TCP；要快、能容忍丢包，选 UDP。

还有一个角度：IP 层只认主机（IP 地址），不认主机上的哪个程序。传输层加了端口号，才把包送到具体的程序手里。浏览器用 80/443，SSH 用 22，DNS 用 53——端口就是程序的门牌号。TCP 和 UDP 各有一套端口，同一个端口号在 TCP 和 UDP 上可以是两个不同的服务。第 10 章会有一张常用端口速查表。

三次握手：建连

TCP 传数据之前，双方要先“打个招呼”，确认彼此都收得到、发得出，这个过程叫三次握手。客户端先发一个 SYN（“我想连你，序号从这儿开始”），服务端回一个 SYN+ACK（“我收到你的了，我也想连你，序号从这儿开始”），客户端再回一个 ACK（“我收到你的了”）。三句话说完，连接才算建立，数据才能开始传。

为什么是三次，不是两次？关键在“双方都要确认对方收得到”。两次握手时，客户端发 SYN，服务端回 SYN+ACK 就算连上——但服务端根本不知道客户端有没有收到自己的回复。更糟的是网络里可能有“迟到”的旧 SYN：客户端早先发的一个 SYN 在路上堵了很久，客户端以为没连上又重发了一个，旧的那个后来才到服务端。两次握手的话，服务端一收到旧 SYN 就建连接、等数据，客户端却根本不知道这回事，白白占着服务端一个连接。三次握手多出来的最后那个 ACK，就是客户端在告诉服务端“我确实收到了你的回复，这次连接是活的”。反过来也一样：没有服务端的 SYN+ACK，客户端也不知道服务端收没收到自己的 SYN。所以三次是最小值——两次不够确认，四次多余。

握手失败意味着什么？发了 SYN 没回音，大概率是对方没开机、端口没开，或者中间的防火墙把包丢了；收到 RST（复位），意思是“这个端口没人听，我拒绝”，比没回音更明确——对方活着，但服务没开。排错时先分清这两种：没回音和被拒绝，指向完全不同的原因。

四次挥手：断连

连接用完了要断开，TCP 用四次挥手。注意：四次挥手是断连，不是“三次握手的对称版”，更不能叫“四次握手”——握手是建连的词，挥手是断连的词，别混了。过程是：一方先发 FIN（“我的数据发完了”），对方回 ACK（“收到，我知道了”），等对方自己的数据也发完了，再发一个 FIN（“我的数据也发完了”），最后第一方回 ACK（“收到，再见”）。每边各发一个 FIN，因为每一边都有自己的“发完”要宣布。

为什么不能像握手那样把中间两步合并成三步？握手的 SYN+ACK 能合并，是因为服务端收到 SYN 时立刻就能回“我也要连你”。挥手不一样：对方收到 FIN 时，自己的数据可能还没发完——它只能先回 ACK 说“知道了”，等数据发完才能发自己的 FIN。中间这段时间叫“半关闭”：一方不发了，另一方还能继续发。服务器发大文件时就常这样：客户端说“我没要发的了”，服务器继续把剩下的数据推完再断。

TIME_WAIT：断了之后还要等一会儿

四次挥手的最后一步，主动关闭方发完 ACK 之后，并不会立刻把连接忘掉，而是进入 TIME_WAIT 状态，等上一段时间（2MSL，MSL 是报文在网络里能存活的最长时间，一般 30 秒到 2 分钟，各系统不同，所以 TIME_WAIT 通常是 1 到 4 分钟）才真正释放。为什么要有这个等待？两个原因。第一，最后那个 ACK 可能在路上丢了，对方收不到就会重发 FIN——如果这边已经把连接忘了，重发的 FIN 到了也没人理，对方会一直重试；留在 TIME_WAIT 里，就能再回一个 ACK。第二，网络里可能还飘着这个连接的“残留包”——旧数据包迟到了，万一马上又建了一个一模一样的连接（同一对 IP 和端口），残留的旧包会被当成新连接的数据，造成错乱。等 2MSL，就是等这些残留包死透，网络里再也没有这个连接的旧包了，才算干净。

所以在电脑上看到一堆 TIME_WAIT 连接，不用慌，这是正常的、健康的表现。真正要警惕的是反面：TIME_WAIT 太多（几万个）会占满端口，让新连接建不起来——服务器被 SYN 泛洪攻击时，半开连接和 TIME_WAIT 堆积就是症状之一，第 12 章会讲到。

TCP 的可靠靠什么

TCP 的“可靠”不是一句口号，是四样机制拼出来的：序号——每个字节都有编号，收到的数据按序号排好，乱序的包能排回原位，重复的包能认出来扔掉；确认——收到数据要回 ACK，没收到 ACK，发送方就知道“可能丢了”；重传——等不到确认就重发，直到对方确认收到为止；校验和——每个报文都带一个校验值，收到先算一遍，对不上就说明路上被改坏了，直接扔掉等重传。数据错了能发现、丢了能补发、乱了能排好——四样齐了，才叫可靠。

可靠是有代价的：握手要时间、确认要来回、重传要等超时。局域网里这点代价不明显，跨洋链路上就明显了：每确认一次都要等一个来回，速度就被往返时间拖住了。下一章讲的窗口和拥塞控制，就是在“可靠”和“快”之间找平衡。

UDP：快在哪里，丢了谁负责

UDP 不握手、不确认、不重传、不排序：应用想发就发，内核直接包好交给 IP。没有握手的等待，没有确认的来回，所以延迟低、开销小，快就快在这里。代价也明明白白：包丢了，UDP 不知道，也不管；包乱序了，UDP 不排；包错了，校验和对不上就扔掉，照样不管。丢了谁负责？谁用 UDP，谁自己负责——应用层自己决定：DNS 查不到就再问一次，视频通话丢几帧就跳过去，游戏丢了位置包就等下一个。换句话说，UDP 把“可靠”这件事交给了用它的应用。

这也解释了为什么 DNS 用 UDP：一个查询一个回答，丢了再问一次就是了，握手反而浪费时间。而网页、文件传输用 TCP：丢一个字节都不行，必须可靠。

什么时候用 TCP，什么时候用 UDP

问自己两个问题：数据丢了能不能接受？晚到有没有意义？丢不得的——网页、文件、邮件、登录、支付，用 TCP。丢一点没关系、晚了就没用的——语音视频通话、直播、在线游戏、DNS 查询，用 UDP。还有一类是“查一下就走”的短查询：DNS、NTP 对时，都是 UDP 的典型用户。

出问题意味着什么？TCP 连不上，先看是没回音（路不通或被防火墙挡）还是收到 RST（对方端口没开）；连上了但传得慢、时断时续，多半是丢包在重传，问题在链路质量或拥塞，第 6 章会展开。UDP 的应用“查不到、收不到”，先别怪路：UDP 没有“连不上”这个概念，查不到可能是对端没回、被防火墙按端口拦了，或者查询本身就丢了——多试一次，换个方式验证，别急着下结论。

还有一个第 6 课就埋下的伏笔：第 6 课的 ping 用的是 ICMP，只能测“路通不通”，测不了 TCP。ping 通了，只能说明 IP 层到了对方；对方的网站端口没开、TCP 被防火墙挡了，ping 照样通。所以“ping 得通但网站打不开”一点不奇怪：ping 和网站走的根本不是同一条验收标准。测 TCP 通不通，要用 TCP 的办法——比如连一下端口，看握手能不能完成。

老师经验：现场排错时，我从不只看 ping。用户说“网站打不开”，我先 ping：通，说明路没问题；再连一下 443 端口：握手半天没反应，多半是防火墙把 TCP 拦了；立刻收到 RST，说明服务根本没起来——这两个结果修的方向完全不同。还有一次，客户的软件隔几分钟就断线重连，抓包一看，连接全卡在 TIME_WAIT 堆积上：程序每次请求都新建连接、用完就关，端口被 TIME_WAIT 占满，新的连不上。改成连接复用，问题就没了。记住：半开连接堆积、RST 满天飞、TIME_WAIT 成千上万，这三种现象背后，十有八九不是“网不好”，而是程序或攻击在作怪。

动手做

1. 在虚拟机里打开终端，跑 python3 -m http.server 8000 起一个本地网页服务；再开一个终端，跑 curl -v http://127.0.0.1:8000/，看输出里 TCP 连接建立、发请求、收响应的全过程。
2. 在虚拟机里跑 ss -tn（Linux）或 netstat -an（Windows），找一找自己电脑上的连接状态：ESTABLISHED 是正在用的，TIME_WAIT 是刚断开在等的，LISTEN 是在等别人连的。
3. 在虚拟机里用 Python 写一对 TCP 收发：服务端监听 127.0.0.1:9000，客户端连上去发一句话，再看服务端收到的是不是原样——然后故意把客户端先关掉，看服务端这边会看到什么状态。
4. 对比一下 UDP：用 Python 的 socket 发一个 UDP 包到 127.0.0.1:9001（那边没人监听），看发送端报不报错——答案是：不报错。UDP 发出去就不管了，这就是它和 TCP 最直观的区别。

避坑

别把“三次握手”和“四次挥手”说成一对对称的东西：握手是建连，挥手是断连，挥手没有“四次握手”这种说法；别以为 ping 通就等于服务正常：ping 走 ICMP，测不了 TCP 端口开没开；别看到 TIME_WAIT 就以为中毒了：它是 TCP 正常断连后的等待，是保护机制；别在 UDP 上指望可靠：用 UDP 的应用丢包要自己处理，写程序时别忘了这一层；别拿真实网站练手：所有实验都在虚拟机和自己的电脑上做，只连 127.0.0.1 这类本地地址。

握手和挥手只是 TCP 的一半：连接建起来之后，数据以多快的速度发、网络堵了怎么办，是第 6 章：TCP 拥塞控制与流量控制的事。回头看第 3 章的 IP 选路：IP 只负责把包送到，送不送得到、送得快不快，是这一章的 TCP 和下一章的窗口说了算。

本课小结
  • 三次握手是建连：SYN → SYN+ACK → ACK，三次是最小值，因为双方都要确认对方收得到。
  • 四次挥手是断连：每边各发一个 FIN，中间两步不能合并，因为对方可能还有数据要发完。
  • TIME_WAIT 是主动关闭方断连后的等待（2MSL），等最后的 ACK 可能重发的 FIN 和网络里的残留包死透。
  • TCP 可靠靠序号、确认、重传、校验和四样机制；UDP 不握手不确认不重传，丢了由用它的应用自己负责。
  • 丢不得的用 TCP，能容忍丢包、晚了就没用的用 UDP；ping 只能测通不通，测不了 TCP 端口开没开。
