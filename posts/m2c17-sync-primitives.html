模块二第 17 章：同步原语深入：信号量、管程、条件变量与死锁检测

操作系统2026-11-25 · 模块二

第 5 章讲过锁、死锁和竞态条件：多个线程同时碰同一块数据会出问题，锁是把“一次只许一个人进”的门。但锁不是唯一的同步工具，有些问题用锁写起来很别扭，有些问题光靠锁还解决不了。这一章讲锁之外的同步工具：信号量、管程、条件变量、屏障和自旋锁，再讲死锁发生之后怎么办——检测与恢复，以及银行家算法的思想。

先把“同步”和“互斥”两个词分开。互斥（mutual exclusion）是“一次只许一个人进”——保护共享数据不被同时改坏。同步（synchronization）是“按顺序来”——A 做完了 B 再做，生产者生产了消费者再消费。锁主要解决互斥，本章的工具主要解决同步。很多真实 bug 都是只做了互斥、忘了同步：数据是没被同时改坏，但消费的线程在生产者还没生产出来时就去拿了，拿到的是空的。

信号量：一个计数器，两种操作

信号量（semaphore）是 Dijkstra 发明的同步工具，本质上是一个计数器，配两个原子操作：P 操作（也叫 wait）和 V 操作（也叫 signal）。P 操作是“申请一个资源”：计数器减 1，如果减完之后计数器还是大于等于 0，申请成功，继续跑；如果变成负数，说明资源不够了，当前线程阻塞，等别人释放。V 操作是“释放一个资源”：计数器加 1，如果有线程在等，就唤醒其中一个。P 和 V 必须是原子的——不可打断，否则两个线程同时 P，计数器就乱了。

信号量分两种。计数型信号量（counting semaphore）：计数器初值是 N，表示一共有 N 个同样的资源，比如一个停车场有 5 个车位，初值就是 5，进一辆减 1，出 一辆加 1。二值信号量（binary semaphore）：计数器只在 0 和 1 之间变，初值是 1，用法和互斥锁几乎一样——P 就是上锁，V 就是解锁。区别在于，二值信号量没有“谁上的锁只能谁解”的规矩，任何线程都可以 V；而互斥锁一般要求上锁的线程自己解锁。

信号量最经典的例子是生产者—消费者问题：一个缓冲区最多放 5 个东西，生产者往里放，消费者往外取。用两个信号量：empty 初值 5，表示空位有几个；full 初值 0，表示货物有几个。再加一把互斥锁，保护“放”和“取”这两个动作本身。生产者先 P(empty)——没空位就等着；放好货，V(full)——告诉消费者多了一个。消费者先 P(full)——没货就等着；取走货，V(empty)——告诉生产者多了一个空位。注意顺序：P(empty) 和 P(锁) 的顺序不能反——先拿锁再等空位，锁就被一个等空位的生产者占住了，消费者想取货也拿不到锁，整个系统卡死。这类“顺序反了就死锁”的 bug，在真实代码里非常常见。

管程与条件变量：把锁和等待打包在一起

管程（monitor）是把“共享数据 + 操作这些数据的过程 + 一把锁”打包在一起的结构：同一时间只有一个线程能在管程里面执行，其他线程想进来就得在门口等。Java 里的 synchronized 方法、Go 里的 sync.Mutex 配着结构体用，背后都是管程的思想。管程的好处是程序员不用到处记得上锁解锁——进了管程就是上了锁，出了管程就是解了锁，锁的范围清清楚楚。

条件变量（condition variable）是和锁配着用的“等待室”：线程发现条件不满足（比如缓冲区空了），就到条件变量上等着，顺便把锁放掉，让别的线程能进来干活；别的线程把条件变满足了（比如生产者放了货），就通知等待室里的线程“可以来看看了”，被唤醒的线程重新拿锁、再检查一次条件。关键细节是“再检查一次”：被唤醒不等于条件一定满足——可能另一个消费者抢先把货取走了，所以唤醒之后必须用 while 循环再判断一次条件，而不是 if 判断一次就往下走。写成 if 是并发编程里最常见的 bug 之一。

屏障（barrier）是另一种同步：所有线程都到齐了才能一起往下走，像赛跑的起跑线——发令枪响之前，谁也不许先跑。并行计算里分阶段的任务常用它：第一阶段所有线程算完，到屏障集合，再一起进入第二阶段。自旋锁（spinlock）则是“不等、一直问”：拿不到锁的线程不睡觉，原地循环不停地试——适合锁只会被占用很短时间的场景（比如内核里几行代码的临界区），如果临界区很长，自旋就是在白白烧 CPU，第 16 章讲的调度器会看到它占着 CPU 不放手。

死锁检测与恢复：死锁发生之后怎么办

第 5 章讲过死锁的四个必要条件：互斥、占有并等待、不可抢占、循环等待。预防是打破其中一个条件，检测则是承认死锁可能发生、事后发现并处理。检测的办法是画一张资源分配图：线程是圆圈，资源是方框，谁占着谁、谁等着谁都画成箭头；图里出现环，就是死锁。操作系统或数据库会定期跑这个检测，发现环了就处理。

恢复有三种办法。第一，抢占资源：从死锁的某个线程手里强行拿走一个资源给别人，打破“不可抢占”——数据库常这么干，代价是被抢的线程要回滚重做。第二，杀掉进程：挑一个死锁里的进程杀掉，释放它的资源；杀一个不够就再杀一个，直到环断开——简单粗暴，但被杀的进程的工作全丢了。第三，回滚：把死锁的线程回滚到之前的一个检查点，释放一部分资源，再重试。三种办法都有代价，所以很多系统（包括大多数操作系统）干脆不检测：死锁了就让它死锁着，等用户重启——这就是所谓的“鸵鸟策略”，听起来消极，但对桌面系统来说，死锁概率低、检测成本高，确实是现实的选择。

银行家算法（Banker's algorithm）是另一种思路：分配之前先算一算——如果这次分配之后，系统还能找到一个顺序，让所有线程都拿到所需的资源跑完，那这次分配就是“安全”的，可以给；如果分配之后可能走到死锁，那就先不给，让申请的线程等一等。它得名于银行放贷：银行手里的钱有限，放贷之前要算算，万一所有储户同时来取钱，银行还付不付得起。银行家算法的问题是，它要求事先知道每个线程最多需要多少资源——现实里程序自己都不知道，所以它更多活在教科书和数据库的锁管理器里，而不是通用操作系统里。但它的思想值得记住：做分配决策之前，先问一句“给了之后，系统还安全吗？”

老师经验：竞态条件是我见过最难复现的 bug，也是安全漏洞里最值钱的一类。第 5 章讲的 TOCTOU（先检查、后使用）就是竞态条件的漏洞版：程序先检查“这个文件是安全的”，再去打开它——检查和打开之间隔了一瞬间，攻击者就在这一瞬间把文件换成了一个链接，指向系统关键文件，程序打开的就不再是它检查过的那个文件。修这类问题不能靠“检查得更仔细”，要靠原子操作：打开文件时直接要求“不要跟随链接”，检查和打开变成一个动作，中间没有时间差。还有一条现场经验：多线程程序出问题，先别急着加锁，先问“共享的是什么、谁在读写、顺序有没有要求”——只加互斥、不补同步，bug 会从“数据错了”变成“程序卡住了”，更难查。死锁现场最有用的工具是线程转储（thread dump）：它会告诉你每个线程在等哪把锁、拿着哪把锁，两张表一对，环就现形了。

动手做

全部在虚拟机里做，用 Python 写，不用装任何东西。1. 写一个生产者—消费者程序：用 Python 的 threading.Semaphore 做 empty（初值 5）和 full（初值 0），再加一把 threading.Lock；生产者每 0.5 秒生产一个数字放进列表，消费者每 0.7 秒取一个打印出来，跑 20 秒，观察缓冲区满了生产者会不会停下来等、空了消费者会不会停下来等。2. 故意把生产者里 P(empty) 和拿锁的顺序反过来（先拿锁再 P(empty)），跑一次，看程序是不是卡住了——卡住后按 Ctrl+C 停掉，体会“顺序反了就死锁”。3. 写一个条件变量的小例子：一个线程等“水烧开”（用 threading.Condition），另一个线程 3 秒后把水烧开并通知，观察等待的线程是不是在通知后才继续。4. 在虚拟机里的 Linux 上跑 cat /proc/locks，看系统当前有哪些文件锁，再想一想：文件锁和内存里的锁，解决的是不是同一个问题？

避坑

信号量的 P 和 V 要配对：P 了不 V，资源就永远少一个，最后所有线程都等死；条件变量唤醒后要用 while 再检查一次条件，不要用 if——被唤醒不等于条件满足了；先拿锁再等资源是死锁的常见写法：等资源之前先把锁放掉，或者调整顺序，先 P 信号量再拿锁；自旋锁只适合很短的临界区，临界区长还自旋，就是在烧 CPU；银行家算法要求事先知道最大需求量，现实程序往往给不出来，所以它是指导思想，不是万能药；竞态条件的修法是原子操作，不是“检查得更仔细”。

同步工具到这里就齐了：锁管互斥，信号量、条件变量、屏障管顺序。下一章钻到磁盘里面去：第 18 章：文件系统内部——文件存在磁盘上到底长什么样，删掉的文件为什么还能恢复。

本课小结
  • 信号量是一个计数器配 P/V 两个原子操作：计数型管 N 个同样的资源，二值信号量用法接近互斥锁，但没有“谁上锁谁解锁”的限制。
  • 生产者—消费者问题要两样东西：信号量管“有没有货、有没有空位”，互斥锁管“放取动作别同时改”，顺序反了会死锁。
  • 管程把共享数据、操作和锁打包在一起；条件变量是配着锁用的等待室，唤醒后要用 while 再检查一次条件。
  • 死锁检测靠资源分配图找环，恢复靠抢占、杀进程或回滚；很多桌面系统干脆不检测，等用户重启。
  • 银行家算法是分配前先算“给了之后还安全吗”，思想是做决策前先评估最坏情况，但它要求事先知道最大需求量。
