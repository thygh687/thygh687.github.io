Linux 管理专项第 6 章：日志与 journald

Linux 管理专项2026-11-25 · Linux 管理专项

出了问题去哪翻记录？Linux 的答案是日志：谁登录过、哪个服务崩了、防火墙拦了谁、SSH 被谁试过密码，全记在日志里。这一章讲 Linux 的日志体系：传统的文本日志、systemd 的 journald、日志轮转和长期保存。

日志是安全工作的“黑匣子”：出事之前看日志能发现苗头，出事之后看日志能还原经过。不会看日志的管理员，出事了只能靠猜；会看日志的，出事了按时间线一捋，事情就清楚了。

这一章和 Windows 专项第 8 章是对应的：那边是事件查看器 + Sysmon，这边是文本日志 + journald。两边的思路一样：先定时间范围、按服务过滤、画时间线。

日志存在哪：文本日志与 journald

传统 Linux 日志是 /var/log/ 下的文本文件：auth.log（登录与 sudo 记录，Debian/Ubuntu）、secure（RHEL 系的同类日志）、syslog（系统总日志）、kern.log（内核日志）、各服务的专属日志（比如 nginx 的 access.log、error.log）。这些文件用 cat、less、grep 就能看。

systemd 的机器上还有 journald：它收集所有服务的日志，存在二进制的 journal 文件里（/var/log/journal/），用 journalctl 命令查。journald 的好处是：日志带结构化字段（服务名、优先级、时间戳精确到微秒），能按服务、按时间、按级别过滤，比 grep 文本文件方便得多。

两者不是互相替代，而是互相补充：journald 是 systemd 服务的日志总入口，文本日志是各服务的原始记录。查问题时两个地方都要会看。

journalctl：最常用的查日志命令

journalctl 的常用姿势：journalctl -u 服务名看某个服务的日志（比如 journalctl -u ssh）；journalctl --since "2026-11-25 09:00" --until "2026-11-25 10:00" 按时间范围查；journalctl -p err 只看错误级别；journalctl -f 实时跟随（像 tail -f）；journalctl --no-pager | grep 关键词全文搜索。

查登录记录：journalctl -u ssh | grep Failed 看 SSH 登录失败；last 命令看最近的登录记录（从 /var/log/wtmp 读）；sudo grep sudo /var/log/auth.log 看谁用 sudo 干了什么。这三条是服务器安全检查的日常。

journalctl 的日志默认存在内存里（重启就丢），要长期保存得改配置：/etc/systemd/journald.conf 里 Storage=persistent，再建 /var/log/journal/ 目录。生产服务器一定要开持久化，否则重启之后出事了就没日志可查。

日志轮转与长期保存

日志轮转（logrotate）是防止日志把磁盘写满的机制：日志文件长到一定大小或一定天数，就压缩归档、开新文件，旧文件按配置保留几份、删几份。配置在 /etc/logrotate.conf 和 /etc/logrotate.d/ 下。

安全上的要点是：日志要保留足够久（至少能覆盖一次事件调查的时间窗口，一般建议几个月），重要日志要异地备份（只存在本机上的日志，攻击者得手后可以删掉、改掉）。有条件的服务器会把日志实时发到集中的日志服务器（比如 rsyslog 远程收集），本机日志被清了，远端还有一份。

还要定期检查磁盘空间：df -h 看看 /var/log 占了多少，日志把磁盘写满会导致服务起不来——这本身就是一种故障。

翻日志的基本功：时间线

和 Windows 那边一样，翻日志先定时间范围、按服务过滤、最后画时间线：几点几分谁登录了、几点几分哪个服务重启了、几点几分防火墙拦了谁，按时间排成一条线，异常点自然就露出来了。

举个例子：凌晨 3 点 auth.log 里出现大量 SSH 登录失败（Fail2ban 的日志里能看到封了哪个 IP），紧接着 SSH 登录成功了一次，接着 sudo 日志里出现一条新建用户的记录——三个点连起来，就是一次入侵的轮廓。单看任何一条，都可能觉得“只是失败了几次”，连起来看才知道出事了。

最后提醒：日志本身也要保护。/var/log/ 的权限要设好，不让普通用户读敏感日志、更不让普通用户清日志。日志被清过本身，就是一条重要线索。

本章检查清单

□ journalctl 查日志：-u 按服务、--since 按时间、-p 按级别、-f 实时跟随。

□ 把本章的命令和检查步骤抄进自己的笔记，下次遇到同类问题直接用。

老师经验：我查过的一起事件里，服务器半夜被人新建了一个账号。翻日志的顺序是：先 last 看登录记录，找到凌晨 3 点的一次 SSH 登录成功；再 journalctl -u ssh 看那次登录前后有没有大量失败（有，Fail2ban 封过那个 IP，但攻击者换了 IP 又来了）；再 grep sudo 看新建账号的命令是谁跑的。三条日志一对，事情就清楚了：弱密码的 SSH 账号被猜中了。我的经验是：日志要平时就看，别等出事了才翻——每天花五分钟看一眼登录失败和服务报错，苗头出现的第一天就能发现。

动手做

1. 只在你自己的 Linux 虚拟机里：运行 journalctl --since "1 hour ago" --no-pager | head -30，看看最近一小时的日志；再运行 journalctl -u ssh --no-pager | tail -20，看看 SSH 服务的日志。
2. 在虚拟机里运行 last | head -10，看看最近的登录记录；再运行 sudo grep -i failed /var/log/auth.log | tail -10（或 journalctl -u ssh | grep -i failed），看看有没有 SSH 登录失败。
3. 在虚拟机里看看日志轮转配置：cat /etc/logrotate.conf，再 ls /etc/logrotate.d/，看看哪些服务配了轮转；再运行 df -h，看看 /var/log 占了多少磁盘。

避坑

别在生产系统、别人的服务器上练日志命令：动手只在你自己的虚拟机里做；journald 默认存在内存里：不开持久化，重启之后日志就没了，重要服务器一定要开；日志要定期看、定期备份：只存在本机上的日志，攻击者得手后可以删掉；别只看一条日志下结论：登录、服务、防火墙三条对上，才算一条证据链。
