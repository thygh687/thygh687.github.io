模块七第 22 章：API 安全：OWASP API Top 10

Web 安全与渗透测试2026-11-25 · 模块七

前面的章节里，网站是“页面”：浏览器打开一个网页，服务器返回 HTML。但现在的系统越来越多是“前端 + 接口”：手机 App、小程序、网页前端，背后都是一个个 API（应用程序接口）在传数据——查订单、改头像、转积分，全是 API 调用。攻击者也跟着变了：不去翻页面，直接去翻接口。这一章讲 OWASP API Security Top 10（2023 版），这是 API 世界的漏洞排行榜，也是你以后做 API 测试的检查清单。

先理解 API 和普通网页的区别：网页是给人看的，API 是给程序用的。网页会把按钮藏起来、把不该点的链接不显示；API 不会——接口地址、参数名、返回的字段，全都明明白白写在请求里。攻击者拿到一个 API 地址，就能自己拼请求、改参数、一个一个试。API 安全的核心问题就一句话：服务器有没有在每一次请求上都认真核对“你是谁、你能干什么”。很多 API 的漏洞，都是因为服务器只在前端页面上做了检查，而在接口上没做——前端不显示删除按钮，不等于接口拒绝删除请求。

最危险的三条：越权、认证与数据过度暴露

API1 失效的对象级授权（BOLA）是 API 漏洞里的头号杀手。举个例子：你登录后访问 /api/orders/123 看自己的订单，把 123 改成 124，就看到了别人的订单——服务器只验证了“你登录了”，没验证“这个订单是不是你的”。防御：每次请求都要核对“这个对象属于当前用户吗”，对象 ID 绝不能只靠前端传来的数字说了算。

API2 失效的认证：API 的认证常常比网页更脆弱——令牌长期有效、令牌可以暴力猜解、忘记密码的接口没有限流。防御：令牌要短有效期、要能吊销，登录和重置密码接口要限流，密码按 NIST SP 800-63B Rev.4 的要求（单独使用的密码至少 15 位，强制查泄露密码库）。

API3 过度的数据暴露：接口返回了比前端需要多得多的数据——前端只显示用户名，接口却把手机号、身份证号、内部备注全返回了。攻击者不需要越权，只需要正常调用接口，就能把多余的数据全拿走。防御：接口只返回前端真正需要的字段，多余的字段坚决不返回。

剩下的七条

API4 缺乏资源与速率限制：接口不限流，攻击者可以一秒发几千个请求，把服务器打垮，或者用暴力猜解慢慢试密码。防御：限流、限并发、限制单个请求的大小。API5 失效的功能级授权（BFLA）：普通用户直接调用了只有管理员能用的接口，比如 /api/admin/delete-user——前端没显示这个按钮，但接口没拦。防御：每个接口都要按角色核对权限，BOLA 管“对象”，BFLA 管“功能”，两个都要查。API6 批量分配（Mass Assignment）：接口直接把请求里的 JSON 字段往数据库对象上贴，攻击者在请求里多加一个 "is_admin": true，就把自己升成管理员了。防御：只接受白名单里的字段，多余字段一律丢弃。

API7 安全配置错误：调试接口没关、错误信息把堆栈和内部路径全吐出来、用了默认密码。防御：生产环境关调试、错误信息只给通用提示、按基线检查配置。API8 注入：和第 2 章的 SQL 注入一个道理，接口参数没过滤就拼进查询里——只不过注入点从网页表单换成了 API 参数。防御：参数化查询、输入验证。API9 不当的资产管理：旧版本接口（v1）还在跑，新版本（v2）修了漏洞，但攻击者继续调旧接口；测试环境的接口也暴露在公网上。防御：给所有接口建台账，下线旧版本，测试接口不对外开放。API10 不安全的第三方 API 消费：你的系统调用了别人的 API，却不验证对方返回的数据——对方返回什么你就信什么。防御：验证、过滤、限制第三方返回的数据，别盲目信任。

老师经验：我测过的 API 里，BOLA 的出现频率高得吓人——十个系统里有七八个能用“改 ID 看别人的数据”的办法打出问题。原因很简单：开发写接口时想的是“前端只会传当前用户的 ID”，忘了攻击者可以直接拼请求。所以我给开发提的检查只有一句话，写在接口文档的每一页：这个接口收到请求时，有没有拿“当前登录的用户”和“请求要操作的对象”比对过？没有比对，就是 BOLA。另外提醒一句：API 测试别只测“正常流程”——正常流程是开发测过的，你要测的是“改一个参数会怎样、换一个用户会怎样、去掉令牌会怎样”，这三个问题问遍所有接口，漏洞就出来一半了。

动手做

1. 只在你自己的靶场虚拟机里：找一个带 API 的开源靶场（比如 OWASP Juice Shop 这类本地靶场），用浏览器开发者工具看它发了哪些 API 请求，把请求地址和参数抄下来。
2. 只在你自己的靶场虚拟机里：用 Burp Suite（第 10 章的工具）拦截一个“查看自己订单”的 API 请求，把订单 ID 改成别人的，看服务器拦不拦得住——这就是在测 BOLA。
3. 只在你自己的靶场虚拟机里：对同一个接口做三件事——去掉认证令牌再发一次、换成另一个用户的令牌再发一次、在请求里多加一个不在文档里的字段再发一次，记录服务器的三种反应。
4. 按本章的十条，写一张你自己的“API 测试检查清单”，每条写一句“怎么测”和一句“怎么算有问题”。

避坑

别只测网页不测接口：前端藏起来不等于接口拦住了；别只用一个账号测：BOLA 和 BFLA 一定要用两个不同权限的账号交叉测；别忽视返回数据：接口多返回一个字段，就是一次数据泄露；别忘了旧版本接口：v1 没下线，v2 修得再好也没用；所有测试只在自己的靶场虚拟机里做，绝不拿真实网站的 API 练手。

API 的地图已经有了：十条里前三条最要命，BOLA 是头号杀手，核心问题永远是“每次请求都核对了吗”。下一章（第 23 章）把 API 再往深处挖：GraphQL 和 JWT——两种现在最常见的接口技术，各自的攻击手法是什么。

本课小结
  • API 是给程序用的接口：地址、参数、返回字段全写在请求里，攻击者可以直接拼请求试。
  • API1 BOLA 是头号杀手：改对象 ID 就能看别人的数据；防御是每次请求核对对象归属。
  • API2 认证失效与 API3 数据过度暴露：令牌要短有效期、可吊销，接口只返回需要的字段。
  • API4–API6：不限流、功能越权、批量分配；API7–API10：配置错误、注入、旧接口未下线、轻信第三方。
  • API 测试三问：改一个参数会怎样、换一个用户会怎样、去掉令牌会怎样。
