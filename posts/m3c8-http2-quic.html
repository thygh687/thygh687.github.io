模块三第 8 章：HTTP/2、HTTP/3 与 QUIC

计算机网络2026-11-25 · 模块三

上一章讲了 HTTP 一问一答的样子，但那是 HTTP/1.1 的样子——一个连接一次只能传一个文件，传完才能传下一个。一个现代网页有几十个文件：HTML、样式、脚本、图片、字体。按 1.1 的规矩，一个一个排队传，页面打开就慢。HTTP/2、HTTP/3 和 QUIC，就是为了解决“慢”而长出来的新协议。学它们不只是追新：排错时看到协议版本、看到连接迁移，才能明白为什么有的网站快、有的场景不断线。

HTTP/1.1 的毛病：队头阻塞

HTTP/1.1 最大的毛病叫“队头阻塞”（Head-of-Line Blocking）。一个 TCP 连接上，请求是一个接一个排队的：前一个响应没传完，后一个请求只能等着。排头的那个文件如果很大、或者丢包重传了，后面所有文件都跟着堵——就像一条单车道，头车抛锚，整条路都动不了。浏览器想了个笨办法：同时开好几个连接（一般 6 个左右），分头去要文件。但连接一多，握手和慢启动的开销也跟着多，而且每个连接都要单独做拥塞控制，治标不治本。

还有一个毛病是头部太啰嗦：每个请求都要把一整套请求头（Cookie、User-Agent、Accept 这些）原样再发一遍。页面文件多，请求就多，重复的头占的带宽加起来相当可观。Cookie 越来越大，这个浪费就越来越明显。

HTTP/2：多路复用、头部压缩、服务器推送

HTTP/2 还是跑在 TCP 上，但它换了个玩法，三个改进一次到位。第一，多路复用：一个连接上可以同时传多个文件，数据被切成小帧，帧上标着属于哪个请求，收到的帧按编号拼回去。几十个文件并行传，不用再排队，也不用开一堆连接。第二，头部压缩（HPACK）：请求头只传和上次不一样的部分，重复的头不再重复发，省下来的全是带宽。第三，服务器推送：服务器猜到浏览器接下来会要什么（比如 HTML 里引用的样式文件），不等浏览器开口就主动推过去，省一次来回。

但 HTTP/2 有个天花板：它跑在 TCP 上，TCP 层的队头阻塞它解决不了。TCP 要求数据按序号一个不少、一个不错地交上来：中间丢了一个包，后面的包哪怕都到了，也得等丢的那个重传回来才能继续——HTTP/2 在应用层分得多开，到了 TCP 层还是被一个丢包卡住整条连接。这就是 HTTP/2 没走完的最后一步，也是 HTTP/3 要解决的问题。

QUIC 与 HTTP/3：换一条路走

HTTP/3 的思路很干脆：TCP 层的队头阻塞修不好，那就不用 TCP。QUIC 是跑在 UDP 之上的新传输协议，HTTP/3 就跑在 QUIC 上。QUIC 把 TCP 的可靠机制（序号、确认、重传）和 TLS 的加密直接做进了自己体内：一个连接上多个流，每个流独立——一个流丢包了，只卡住这个流，其他流照常走，TCP 层的队头阻塞从根上没了。

QUIC 还有两个本事。第一，0-RTT：如果客户端以前连过这个服务器，握手时可以直接带着加密数据一起发，第一次往返就能传数据——对比一下：第 7 章的 TLS 1.3 握手要 1-RTT，TCP 握手还要先花一次，QUIC 把建连和加密握手合成一步，熟人之间几乎零等待。第二，连接迁移：QUIC 用一个连接 ID 认连接，不认 IP 地址和端口——你从 Wi-Fi 切换到 4G，IP 地址变了，连接 ID 没变，连接不断，视频不用重连、下载不用重下。TCP 认的是四元组（源 IP、源端口、目标 IP、目标端口），IP 一变连接就断，只能重建。

代价也有：QUIC 在用户态实现，跑在 UDP 上，中间设备（防火墙、运营商）对 UDP 的支持不如 TCP 成熟，有些网络会直接把 UDP 限速甚至封掉——这时候 HTTP/3 会回落到 HTTP/2 甚至 1.1。协议再新，也得看路让不让走。

三代协议对比

为什么新协议还是离不开第 5 章的 TCP/UDP 知识

新协议没有发明新物理，只是把旧机制换了个地方放。QUIC 的可靠还是靠序号、确认、重传——和第 5 章的 TCP 可靠是同一套思想，只是从内核搬到了用户态、从 TCP 搬到了 UDP 上。QUIC 的拥塞控制还是慢启动、拥塞避免那一套，学的还是第 6 章的窗口逻辑。HTTP/2 的多路复用，解决的是应用层排队，但它脚下的 TCP 照样有窗口、照样会拥塞、照样要握手。

更实际一点：排错时你面对的还是那些老概念。HTTP/3 打不开，先问 UDP 通不通——有的防火墙只放 TCP 443，不放 UDP 443，QUIC 连握手都发不出去，只能回落到 HTTP/2。连接迁移不断线，听起来神奇，拆开看就是“连接认 ID 不认 IP”这一句话。学新协议最快的办法，永远是先把旧协议吃透：新东西都是旧东西的重新组合。

老师经验：有一次客户说“手机上视频总卡，电脑上不卡”，查了半天，最后发现是公司的防火墙把 UDP 443 封了——手机浏览器想走 HTTP/3，走不通，回落到 HTTP/2 又要重新握手，来回折腾反而更卡。放开 UDP 443，立刻就好了。还有一次，用户抱怨“切 Wi-Fi 到 4G 视频就断”，那是老应用还在用 TCP：IP 一变连接必断，只能重连；换成支持 QUIC 的应用，切换时几乎感觉不到。排错时先问一句：这条路走的是 TCP 还是 UDP？答案不同，查的方向完全不同。顺便说一句：看到浏览器地址栏显示 HTTP/3，不代表全程都是 QUIC——中间任何一环不支持，都会悄悄回落到 HTTP/2，别被版本号骗了。

动手做

1. 在虚拟机里跑 python3 -m http.server 8000 起一个本地服务，再跑 curl -v http://127.0.0.1:8000/，看响应头里写的是 HTTP/1.1——本地这个简易服务只会 1.1，正好拿它当“老协议”的样子记下来。
2. 在虚拟机里的浏览器打开开发者工具（F12）→ 网络面板，刷新一个你常看的网站，看“协议”那一列：写着 h2 的就是 HTTP/2，写着 h3 的就是 HTTP/3，写着 http/1.1 的就是老协议——只看、不改，记下来哪些站已经用上新协议了。
3. 观察一次连接迁移：手机上正在播的视频，从 Wi-Fi 切换到 4G，看它断不断、卡多久；再对比一个老应用（比如还在用 TCP 长连接的），切换时是不是要重新加载——这就是 QUIC 连接迁移和 TCP 四元组的区别，亲眼看到一次就记住了。

避坑

别以为 HTTP/2 解决了所有阻塞：它只解决了应用层的，TCP 层的队头阻塞还在，丢包一多照样卡；别以为看到 h3 就全程是 QUIC：中间任何一环不支持都会悄悄回落到 h2，版本号只是协商结果；别把 0-RTT 当成免费午餐：第一次连接没有 0-RTT，只有“熟人”重连才有，而且 0-RTT 的数据有重放风险，敏感操作不要走 0-RTT；别忘了 UDP 也会被拦：防火墙封了 UDP 443，HTTP/3 连握手都发不出去，先查 UDP 通不通，再怪协议；别在真实网站上做压测和抓包实验：观察协议版本可以，灌流量、抓别人的包不行，所有动手实验只在虚拟机和自己的电脑上做。

应用层的新协议讲完了，接下来回到网络本身的日常：你每天自动拿到的地址、共享的上网方式，是谁在管——第 9 章：常见网络服务：DHCP、NAT。回头看第 7 章的整条链：DNS、TCP、TLS、HTTP 每一层都有自己的新旧版本，但每一层解决的问题，从第 5 章起就没变过。

本课小结
  • HTTP/1.1 一个连接一次只传一个文件，排头的堵了后面全等，这就是队头阻塞。
  • HTTP/2 靠多路复用、头部压缩和服务器推送提速，但它跑在 TCP 上，TCP 层的队头阻塞还在。
  • QUIC 基于 UDP，把可靠和加密做进自己体内：各流独立、0-RTT、连接迁移，Wi-Fi 切 4G 不掉线。
  • 新协议没有新物理：QUIC 的可靠和拥塞控制，学的还是第 5 章的序号确认重传和第 6 章的窗口逻辑。
  • 防火墙封了 UDP 443，HTTP/3 连握手都发不出去，只能回落到 HTTP/2；看到 h3 不代表全程都是 QUIC。
