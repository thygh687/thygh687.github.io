模块四第 12 章：软件工程与安全编码

编程基础2026-11-25 · 模块四

会写代码和会“做出一个能用的软件”是两回事。一个能用的软件要经历：想清楚要做什么、写出来、测出来有没有 bug、给别人看一遍、上线、出了问题能修。安全工程师既要写自己的小工具（比如后面几章的扫描器、检查器），也要能看懂别人的代码、找出里面的漏洞——这两件事靠的都是同一套软件工程的基本功：调试、测试、代码评审、安全编码。这一章不讲大理论，只讲每天真能用的方法。

从需求到上线：软件是怎么长出来的

一个软件的生命周期通常是五步：需求——到底要解决什么问题，给谁用；设计——拆成哪几个部分，数据怎么流；实现——写代码；测试——验证它是不是真做到了需求说的事；维护——上线之后修 bug、加功能。很多安全漏洞的根子不在“实现”那一步，而在“需求”那一步就没写清楚：需求里没说“密码要多长”，程序员就随便写了个 6 位；需求里没说“用户输入要检查”，程序员就原样拼进了数据库查询。

安全要嵌进每一步，而不是最后贴上去：需求阶段就问“谁能看什么、谁不能看什么”；设计阶段就定“敏感数据怎么存、怎么传”；实现阶段按安全编码规范写；测试阶段专门测“坏输入会不会搞垮它”；维护阶段及时修已知漏洞。事后补安全，十倍的成本都未必补得回来。

版本管理回顾：Git 是安全网

第 18 课讲过 Git 的基本用法，这里补一个安全视角：版本管理是你的“后悔药”。每一次提交（commit）都是一个可以回去的检查点，代码改坏了、删错了、被人改了，都能靠 Git 回到上一个好的版本。好习惯就三条：改一点、提交一次，提交信息写清楚改了什么；别把密码、密钥、真实数据提交进仓库——一旦 push 到网上，等于公开；定期看一眼提交历史，陌生的提交、陌生的作者，都是要警惕的信号。供应链攻击里，攻击者往开源项目里偷偷塞恶意提交的事并不少见，看提交记录就是第一道防线。

调试方法：打印、二分、断点

程序出 bug 时，别盯着屏幕发呆，按顺序用三招。第一招是打印：在关键地方输出变量的值，看程序实际走到哪、算出来什么——很多时候 bug 一眼就现形了。第二招是二分：把出问题的范围对半砍——注释掉一半代码，问题还在不在？在，就再砍一半；不在，问题在另一半。几轮下来，范围就缩到几行。第三招是断点：让程序在某一行停下来，一步一步往下走，看着变量一个一个变。这三招从糙到细：打印最快，二分最稳，断点最准。

调试时还有一个心法：先复现，再修。一个 bug 如果不能稳定复现，你修的很可能不是它。先找到“每次这么操作就一定出问题”的最小步骤，再动手修，修完用同样的步骤验一遍。安全漏洞的修复也一样：先写出能稳定触发漏洞的最小输入，修完再用这个输入验证——这就是后面测试里说的“回归测试”。

测试：单元测试与边界值

测试分很多层，初学者先掌握两种。第一种是单元测试：给一个小函数写几个测试，喂它几个输入，看输出对不对。比如写了个“判断密码长度够不够”的函数，就测：空密码、14 位、15 位、16 位，分别应该返回什么。测试的好处是：以后改代码，跑一遍测试就知道有没有改坏别的东西。

第二种是边界值测试：bug 最爱藏在边界上。密码要求至少 15 位，就要测 14、15、16 位这三个点；输入框最多 100 个字，就要测 99、100、101 个字；数组有 10 个元素，就要测第 0 个、第 9 个、第 10 个（越界了）。攻击者最喜欢的就是边界：缓冲区溢出、整数溢出、越界读取，几乎全是边界没守住。写测试时专门盯着边界测，等于提前站在攻击者的角度想了一遍。

代码评审看什么

代码评审（code review）就是“让另一个人读一遍你的代码再合并”。评审时重点看五样东西：第一，输入有没有检查——所有来自用户、文件、网络的数据都当成不可信的，有没有判空、有没有判长度、有没有判类型；第二，权限有没有越界——这段代码能不能碰到它不该碰的数据；第三，敏感信息有没有泄露——日志里、错误提示里、报错信息里有没有打印密码、密钥、真实路径；第四，边界有没有守住——循环、数组、内存分配，边界条件对不对；第五，看不懂的地方——看不懂的代码就是风险，写清楚、加注释，或者重写。

评审不是挑刺，是两个人一起对代码负责。被评审也别玻璃心：别人指出的问题，十有八九是你自己看了一百遍也看不出来的盲点。安全圈里很多著名漏洞，都是“要是当时有人多看一眼就好了”。

安全编码的头几条规矩

第一，永远不信任输入：用户输入、文件内容、网络数据，全部先验证再使用，长度、类型、范围、格式，一个都不能少。第二，最小权限：程序只拿它必需的权限，能读就别给写，能访问一个目录就别给整个磁盘——第 9 课的权限思想，在代码里也一样。第三，敏感数据不落地：密码不写进日志、不写进代码、不提交进仓库；密钥单独保管，定期轮换。第四，错误信息别说太多：登录失败就说“用户名或密码错误”，别说“这个用户名不存在”——后者等于帮攻击者枚举账号。第五，用现成的、经过检验的库：加密自己别发明算法，用标准库；解析数据用成熟的解析器，别自己拼字符串——自己拼的那一层，常常就是注入漏洞的入口。

老师经验：我审过一份实习生写的登录代码，逻辑全对，唯一的问题是：登录失败时返回的错误信息分两种——“用户不存在”和“密码错误”。攻击者拿着一本用户名字典挨个试，返回“密码错误”的就是真实账号，一晚上能枚举出几百个真实用户名。我让他改成统一的“用户名或密码错误”，再加登录失败次数限制和验证码。还有一次更典型的：一段代码把用户输入直接拼进 SQL 查询，我指给他看，他说“我以为只有管理员能进这个页面”。权限假设是最危险的假设——页面能被谁打开，永远不要靠“以为”，要靠代码里的检查。安全编码的规矩看着琐碎，每一条背后都是一次真实的事故。

动手做

1. 在虚拟机里给第 15 章要写的密码检查器先写三个单元测试：空密码、14 位密码、15 位密码，分别应该得到什么结果——先写测试，再写功能，体会“测试先行”的做法。
2. 找一段你之前写的脚本（比如第 10 章的巡检脚本），用“二分法”故意制造并定位一个 bug：把其中一行改错，看报错信息能不能帮你定位；再把报错信息改得更友好一点。
3. 做一次代码评审练习：把你的巡检脚本发给自己“第二天的自己”——逐行读一遍，按本章的五条检查清单打勾：输入检查、权限、敏感信息、边界、可读性，写下至少两个要改的地方。
4. 在虚拟机里建一个 Git 仓库，把你写的脚本提交进去；再故意往代码里写一行“密码”假装提交，然后用 Git 的历史查看它——体会为什么“别把秘密提交进仓库”是一条铁规矩（提交进历史的东西，删掉文件也还在历史里）。

避坑

别等写完才测试：写一个函数测一个函数，攒到最后一起测，bug 会叠在一起分不清谁是谁；别只测“正常情况”：攻击者永远走不正常的那条路，边界值和坏输入才是测试的重点；别把错误信息写得太热情：报错里别带密码、别带完整路径、别告诉攻击者“这个账号不存在”；别自己发明加密算法或自己拼 SQL：用标准库和参数化查询，现成的轮子比你手写的结实；别跳过代码评审：一个人看自己的代码，盲点永远在那里，多一个人看，就多一双眼睛。

工程方法有了，下一章就直面编程里最硬的一块：第 13 章：C 语言：指针与内存。回头看模块一第 3 章的内存和模块二第 1 章的操作系统——指针就是直接和那两章讲的内存打交道。

本课小结
  • 软件从需求、设计、实现、测试到维护走一圈，安全要嵌进每一步，事后补安全的成本高十倍。
  • Git 是后悔药：小步提交、写清信息、绝不把密码和密钥提交进仓库，提交历史本身就是一道防线。
  • 调试三招：打印最快、二分最稳、断点最准；先稳定复现 bug 再修，修完用同样的步骤验证。
  • 测试先盯边界：15 位密码测 14、15、16 位，攻击者最爱钻的就是边界，缓冲区溢出几乎全是边界没守住。
  • 安全编码头几条：不信任任何输入、最小权限、敏感数据不落地、报错别说太多、用经过检验的标准库。
