模块七第 23 章：API 安全深入：GraphQL 与 JWT 攻击

Web 安全与渗透测试2026-11-25 · 模块七

上一章（第 22 章）我们按 OWASP API Top 10 把接口的漏洞过了一遍。这一章往深处挖两种现在最常见的接口技术：GraphQL 和 JWT。先说一句：这两种技术本身不是漏洞，漏洞出在“用得不对”上——GraphQL 用得不对，等于把数据库的查询权交给了对方；JWT 用得不对，等于把“证明你是谁”的钥匙交给了对方。所有演示只在你自己的靶场虚拟机里做。

先讲 GraphQL。普通的 REST API 是“一接口一功能”：查订单调一个接口，查用户调另一个接口。GraphQL 是“一接口全都要”：客户端发一个查询，写明“我要订单的编号、金额、用户的手机号”，服务器按查询返回——客户端想查什么就查什么。这很灵活，但也带来一个问题：如果服务器不限制查询的内容和深度，攻击者可以一次查走整个数据库。比如一个查询里嵌套十层“用户的好友的好友的好友……”，服务器会老老实实地一层一层查下去，直到被拖垮——这叫深度查询攻击。还有内省（Introspection）：GraphQL 默认允许客户端问一句“你都有哪些字段”，服务器会把完整的接口结构（包括那些前端没用过的敏感字段）全告诉对方——攻击者连猜都不用猜，直接照着清单查。

GraphQL 的攻击面

GraphQL 有四个常见的攻击点。第一，内省泄露结构：生产环境要关掉内省，或者至少不让未登录用户问。第二，深度与复杂度攻击：不限制查询嵌套层数和字段数量，一个查询就能拖垮服务器；防御是设查询深度上限、复杂度上限和超时。第三，批量查询：一次请求里塞几百个查询，绕过按“请求次数”算的限流——限流要按“查询复杂度”算，而不是按请求数算。第四，越权换了个地方：GraphQL 里的 BOLA 和第 22 章讲的一模一样——查询里把用户 ID 一改，就查到了别人的数据；只不过这里改的不是 URL 里的数字，是查询语句里的参数。记住：换了接口形态，越权的问题一个没少。

JWT 攻击：令牌是怎么被伪造的

再讲 JWT（JSON Web Token）。JWT 是现在最常见的 API 令牌格式，它由三部分组成：头部（Header，说“我是用什么算法签名的”）、载荷（Payload，说“我是哪个用户、有什么权限、什么时候过期”）、签名（Signature，服务器用密钥对前两部分算出来的防伪标记）。服务器收到 JWT，先验签名：签名对得上，就相信载荷里写的东西。JWT 的攻击，几乎全是冲着“签名验证”来的。

第一种经典攻击是 alg none（空算法）：攻击者把头部的算法改成 none（意思是“不用签名”），再把载荷里的用户改成管理员，服务器如果接受了“不用签名的令牌”，就等于谁都能伪造身份。防御：服务器只接受白名单里的算法，绝不接受 none。第二种是弱密钥爆破：如果服务器签发 JWT 用的密钥是弱密码（比如 123456），攻击者可以离线暴力猜出密钥，然后自己签发任意令牌。防御：密钥要用长随机串，定期更换。第三种是 kid 与 jku 注入：JWT 头部有个 kid 字段（说“去哪找验证用的密钥”）和 jku 字段（说“密钥的地址是这个 URL”），如果服务器不加验证就按攻击者给的地址去取密钥，攻击者就能让服务器用攻击者自己的密钥验签——自己签、自己验，当然通过。防御：kid 只允许白名单里的值，jku 只允许信任的地址，绝不接受用户提供的密钥地址。第四种是令牌长期有效、不吊销：JWT 一旦签发，在过期之前服务器没法单独作废它——用户改了密码、丢了账号，旧令牌照样能用。防御：令牌有效期设短，重要操作重新验证身份，关键场景用服务端维护的吊销列表。

老师经验：JWT 有一个新手最容易踩的坑：以为“JWT 是加密的”。不是——JWT 默认只是编码，不是加密，载荷里的内容任何人解码都能看到（签名防的是篡改，不是偷看）。所以千万别把敏感信息（比如密码、身份证号）放进 JWT 的载荷里。另一个坑是把 JWT 当成“万能钥匙”：有效期设成 30 天、永不过期，一旦泄露就是一个月的通行证。我给开发的建议就三条：有效期按分钟算（比如 15 分钟），配一个刷新令牌机制；密钥用长随机串，放进密钥管理系统，别写在代码里；验签只认白名单算法，none 永远不接受。这三条做到了，JWT 的大部分攻击就没戏了。

动手做

1. 只在你自己的靶场虚拟机里：找一个带 JWT 的本地靶场，登录后复制你的 JWT，用在线解码思路（或本地工具）把它拆成三部分，读出头部和载荷里写了什么，确认载荷里有没有敏感信息。
2. 只在你自己的靶场虚拟机里：把 JWT 载荷里的用户角色改成管理员，但不改签名，再发一次请求，看服务器拦不拦得住——理解“签名防篡改”是什么意思。
3. 只在你自己的靶场虚拟机里：把 JWT 头部的算法改成 none（去掉签名部分），再发一次，看服务器接不接受——理解 alg none 攻击的原理（只在靶场里验证服务器行为，不用于真实系统）。
4. 只在你自己的靶场虚拟机里：如果靶场有 GraphQL 接口，先发一个内省查询，看服务器返回什么；再发一个嵌套很深的查询，看服务器有没有深度限制；把两次结果写进笔记。

避坑

别把 JWT 当加密：载荷是编码过的明文，敏感信息别往里放；别接受 alg none：验签算法只认白名单；别用弱密钥签 JWT：密钥要长随机、定期换、别写代码里；别让令牌长期有效：有效期按分钟算，重要操作重新验证；GraphQL 生产环境要关内省、限深度、按复杂度限流；所有实验只在自己的靶场虚拟机里做。

GraphQL 和 JWT 讲完了：前者的问题是“查得太多”，后者的问题是“签得太松”。下一章（第 24 章）换一个视角：与其一次次在上线之后找漏洞，不如把安全放进开发流程里——DevSecOps，安全要进开发流程。

本课小结
  • GraphQL 一接口全都要：内省会泄露接口结构，深度查询能拖垮服务器，批量查询能绕过按次数算的限流。
  • JWT 由头部、载荷、签名三部分组成；签名防篡改、不防偷看，载荷里别放敏感信息。
  • JWT 四种攻击：alg none、弱密钥爆破、kid 与 jku 注入、令牌长期有效无法吊销。
  • 防御：验签只认白名单算法，密钥用长随机串并定期更换，令牌有效期按分钟算。
  • 换了接口形态，越权问题一个没少：GraphQL 里同样要查 BOLA。
