模块八第 2 章：SIEM 与日志分析

安全运营与应急响应2026-11-25 · 模块八

上一章我们说 SOC 靠工具先过滤日志，只把可疑的推给人看——这套工具的核心就叫 SIEM，全称 Security Information and Event Management，安全信息与事件管理。名字很长，意思很简单：把所有设备的日志收进一个地方，统一存、统一查、统一告警。没有 SIEM，分析师要一台一台机器去翻日志；有了 SIEM，一次查询就能看到“这个 IP 在全公司干了什么”。

先建立一个直觉：日志就是系统的“黑匣子”。电脑每做一件事——谁登录了、哪个程序启动了、哪条防火墙规则拦了谁、哪个文件被改了——都会留下一行记录。攻击者再小心，也很难做到“来过但什么痕迹都不留”；他删掉一部分日志，删除这个动作本身也是痕迹。所以安全圈有句话：日志会说话，关键是你得会听。本章讲 SIEM 是怎么工作的，以及分析师是怎么从日志里把攻击找出来的。

SIEM 的四步流水线

第一步，收集。SIEM 从各种来源收日志：Windows 事件日志、Linux 的 syslog、防火墙、路由器、EDR、杀毒软件、邮件网关、云平台……每种日志格式都不一样，有的是一行文本，有的是 JSON，有的是 Windows 的 EVTX。收集的方式通常是装一个轻量的采集代理（Agent），或者让设备把日志“推”到 SIEM。收集时最容易出的问题是“漏”——某台服务器没装代理，它的日志就永远进不来，出事了也没法查。

第二步，归一化与解析。不同来源的日志写法五花八门：有的写“登录失败”，有的写“4625”，有的写“authentication failure”。SIEM 会把它们翻译成统一的字段：时间、来源 IP、目标 IP、用户名、动作、结果。这样分析师写一条查询，就能同时查所有来源。归一化做得好不好，直接决定 SIEM 好不好用——字段对不上，查询就查不全。

第三步，关联与检测。这是 SIEM 最值钱的一步：把分散的日志拼成一条线。比如“同一账号 5 分钟内在 3 个国家登录”——单看每一条登录成功都没问题，拼起来就是账号被盗的典型信号；再比如“防火墙先放行了一个下载，EDR 随后发现一个陌生进程启动，紧接着有大量数据外发”——三件事单独看都可疑，串起来就是一次完整的入侵链。SIEM 靠关联规则做这件事：规则就是“如果 A 又 B 又 C，就告警”。

第四步，存储与告警。日志要存下来备查——合规要求短则几个月，长则几年。存多久、存哪里、谁能查，都是要事先定好的策略。检测到可疑行为后，SIEM 产生告警，推给 SOC 的告警队列（第 1 章讲过），分析师开始分诊。好的 SIEM 还会给告警打分、标上下文：这个 IP 以前有没有恶名、这个账号平时几点上班——上下文越全，分诊越快。

日志分析的三个基本功

第一，知道去哪找。Windows 上最常用的是事件查看器里的三个日志：安全日志（登录、权限变化）、系统日志（服务、驱动、关机）、应用程序日志（软件报错）。几个关键事件 ID 值得背下来：4624 登录成功、4625 登录失败、4688 新进程创建、4720 新建账号、7045 新装服务、1102 日志被清空——最后一个特别危险：攻击者清日志，就是不想让你看到他干了什么。Linux 上则看 /var/log/auth.log（登录）和 /var/log/syslog（系统）。

第二，会问问题。日志分析不是“从头读到尾”，而是带着问题去查：过去 24 小时有没有登录失败超过 10 次的账号？有没有在非工作时间登录的管理员？有没有从没见过的进程在开机启动？有没有一台内网电脑在半夜往外传大量数据？每个问题对应一条查询——SIEM 的查询语言各家不同，但思路都一样：先定时间范围，再定条件，最后排序看最多的。第 11 章会专门讲 SIEM 的查询语言。

第三，会看时间线。把可疑事件按时间排成一条线，是日志分析最有用的手法：一台电脑先是收到一封钓鱼邮件，十分钟后用户点了链接，接着一个陌生进程启动，然后开始扫描内网——时间线一摆，故事就清楚了。第 5 章我们会拿着真实的模拟日志，完整地排一次时间线破案。

基线：先知道“正常”长什么样

日志分析有个前提：你得先知道“正常”是什么样子，这叫基线（Baseline）。财务部的电脑平时只在工作时间访问财务系统，半夜突然开始扫描内网——没有基线，你不知道这反不反常；有了基线，一眼就能看出来。建立基线的方法很朴素：连续看两周的日志，记下每台重要机器、每个重要账号的日常规律：几点登录、访问哪些系统、流量多大。基线不是一成不变的——公司上了新系统、员工换了岗位，基线就要更新。很多 SIEM 现在用机器学习自动学基线、自动标“偏离”，但原理和人工看是一样的：先懂正常，才能认出异常。

还要提醒一点：日志本身也是要保护的资产。日志里有登录记录、有访问记录，一旦被篡改，事后就没法取证（第 6 章会讲证据链）。所以日志要集中存、只读存、设好访问权限，重要日志还要做完整性保护——攻击者最爱干的事之一，就是入侵之后先清日志。Windows 的事件 1102（日志被清空）本身就是一条高优先级告警：正常运维几乎不会清日志，清日志的人，十有八九心里有鬼。

好规则与坏规则：怎么写一条能用的检测规则

一条好的检测规则有三个特点：准（误报少）、全（覆盖面够）、可行动（告警出来就知道该干什么）。反过来，坏规则也有三个典型毛病：条件太宽——比如“任何登录失败都告警”，一天能刷出上万条；条件太窄——只盯一个具体的 IP 或文件名，攻击者换个 IP 就绕过去了；没有上下文——告警里不写“这是谁的机器、平时正不正常”，分析师拿到手还得从头查。

写规则时有个实用技巧：先写“宽”规则跑一周，只记录、不告警，看看它每天会命中多少次、命中的都是什么；再根据结果收紧条件，把误报最多的那几类排除掉，最后才打开告警。这种“先观察、再告警”的做法叫调优期（Tuning），新规则上线都应该经过调优期。没有调优期直接上线的规则，要么吵得没人看，要么静得抓不住东西。

规则还要定期“体检”：每季度看一次每条规则的命中数和确认率——一条规则三个月命中 0 次，要问是“一直没发生”还是“规则写错了、根本没生效”；一条规则命中上万次但确认率是 0，要问是不是该关掉或重写。规则和日志一样，是需要持续维护的资产，不是写完就一劳永逸的东西。

老师经验：我第一次带新人看 SIEM，最常听到的问题是“我该从哪条日志开始看？”我的答案永远是：从“最不可能正常”的地方开始。新人喜欢从第一条往后翻，翻几百条就晕了；老手是先筛：先看高危告警，再看登录失败最多的账号，再看非工作时间的活动——三板斧下来，80% 的案子都有方向了。还有一个现场教训：有一次我们查到一台服务器半夜有大量数据外发，差点按入侵处理，结果一问，是备份任务改了时间——备份窗口从凌晨两点改到了三点，没人通知 SOC。所以查日志之前，先问一句“最近有没有变更？”（模块六第 21 章的变更管理就是防这种乌龙的），能省掉一半的误报排查。

动手做

1. 只在你自己的虚拟机里：打开事件查看器，筛选安全日志里最近 7 天的事件 ID 4625（登录失败），按账号分组，找出失败次数最多的前 3 个账号，记下来。
2. 在同一台虚拟机上找一条 4624（登录成功），记下它的时间、账号、登录类型和来源 IP——练习从一行日志里读出“谁、什么时候、从哪、怎么”登录的。
3. 给你的虚拟机画一条基线：连续三天，每天同一时间记下开机时间、登录账号和运行的主要程序，第三天对比前两天，看看哪些是规律、哪些是例外。
4. 在虚拟机里故意制造一条“异常”再找到它：比如在深夜（或你平时不用的时间）登录一次，然后在日志里把它找出来——体会“基线之外就是异常”的感觉。

避坑

别从第一条日志往后翻：带着问题查，先筛高危、再筛最多的、再筛非工作时间的；别只看一条日志下结论：单条登录成功可能是正常的，关联起来才看得清；别忽视 1102（日志被清空）：这是攻击者最爱干的事，看到它要当高优先级处理；别忘了日志也要保护：集中存储、只读、设权限，日志被改了就等于证据没了；别在真实系统上练手：所有查询和筛选只在你自己的虚拟机日志上做。

第 1 章我们知道了 SOC 是 7×24 小时盯着屏幕的人，这一章知道了他们盯的是什么——SIEM 里汇集的日志，以及怎么从日志里把攻击拼出来。日志分析的功夫，一半在工具，一半在“先懂正常”的基线思维。下一章我们换个角度：用攻击者的手法来防守——ATT&CK 防御、威胁狩猎与检测工程。

本课小结
  • SIEM 把所有设备的日志收进一个地方：收集、归一化、关联检测、存储告警，四步流水线。
  • 关联是 SIEM 最值钱的能力：分散的日志拼成一条线，单条看正常、拼起来是攻击。
  • Windows 关键事件 ID：4624 登录成功、4625 登录失败、4688 新进程、4720 新建账号、1102 日志被清空。
  • 日志分析三基本功：知道去哪找、带着问题查、按时间排时间线。
  • 基线是前提：先知道“正常”长什么样，才能认出异常；日志本身也要保护，防篡改、防清空。
