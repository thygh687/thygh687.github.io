模块七第 7 章：会话与认证深入：JWT、CORS、CSP 与越权访问

Web 安全与渗透测试2026-11-25 · 模块七

第 1 章我们讲了会话与 Cookie 的基本原理，留了两个伏笔：JWT 是什么、越权访问是怎么回事。这一章把它们全部收束，再加上两个经常和认证一起出现、也经常被配错的机制：CORS（跨源资源共享）和 CSP（内容安全策略）。这四个东西合起来，就是 Web 认证的攻与防——攻击者怎么绕过身份验证，防御者又该怎么把门守住。

先回答一个根本问题：网站怎么知道“你是谁”？有两种主流答案。第 1 章讲过第一种：服务端会话——服务器记得你，浏览器只拿一把会话 ID 钥匙。第二种就是 JWT：服务器把“用户 ID、角色、过期时间”写进一个令牌，用密钥签名后发给你，你每次请求都带着它；服务器验签名，签名对了就认你是令牌上写的那个人。JWT 不用服务器存会话，适合分布式系统，但代价是：令牌一旦发出去，在过期之前没法单独作废——改密码、封账号都撤不回已经发出的令牌，这是它和服务端会话最大的区别。

JWT 的结构与常见攻击手法

一个 JWT 由三部分组成，用点连起来：头部（Header）——写着签名算法，比如 HS256；载荷（Payload）——写着用户 ID、角色、过期时间，注意载荷只是 Base64 编码，任何人都能解开看，别往里面放密码、身份证号这类敏感信息；签名（Signature）——用服务器的密钥对前两部分算出来的“印章”，改一个字签名就对不上。

针对 JWT 的攻击，常见有三种。第一，算法混淆（alg=none）：攻击者把头部算法改成 none（意思是“不用签名”），再把载荷里的角色改成 admin，如果服务器真的接受了无签名令牌，就等于门没锁。第二，弱密钥爆破：HS256 是对称签名，密钥就是服务器和验证方共享的一个字符串；密钥太弱（比如 “secret”、“123456”），攻击者可以离线爆破出来，自己签一个 admin 令牌。第三，密钥混淆：RS256 是非对称签名，验签用公钥；如果服务器错误地用公钥当作 HS256 的密钥来验签，攻击者拿着公开的公钥就能自己签发令牌。防御很明确：服务器只接受白名单里的算法、绝不接受 none；HS256 密钥要足够长、足够随机；RS256 和 HS256 的密钥绝不能混用；令牌有效期要短，敏感操作还要再验一次身份。

CORS：谁可以跨站读我的数据

浏览器的同源策略默认不让一个网站的 JavaScript 去读另一个网站的数据——这是安全基线。但前后端分离的网站确实需要跨站访问，于是有了 CORS：服务器通过响应头 Access-Control-Allow-Origin 声明“哪些来源可以读我的数据”。配错 CORS 的典型样子是：Access-Control-Allow-Origin: * 又加上了 Access-Control-Allow-Credentials: true——意思是“任何网站都能带着用户的 Cookie 来读我的数据”。攻击者做个恶意页面，受害者一打开，页面里的脚本就带着他的 Cookie 去读目标站的数据，再发回给攻击者。防御：Origin 必须写明确的白名单，绝不能是 *；带凭证的跨站请求，Origin 必须是具体域名；只放行确实需要的域名和方法。

CSP：给浏览器立规矩

CSP 在第 3 章已经出场过一次（防 XSS 的第二层），这里把它讲透。CSP 是服务器通过响应头给浏览器立的规矩：脚本只能从这些来源加载、图片只能从这些域名来、页面不许被嵌进 iframe（防点击劫持）。一个严格的 CSP 像这样：default-src 'self'; script-src 'self'——只允许本站的资源。配 CSP 的常见错误是图省事写 unsafe-inline（允许页面里的内联脚本），这等于把防 XSS 的门又打开了一半。正确的做法是从严开始，逐个放行确实需要的来源，配合 report-uri 先收集违规报告再收紧。

越权访问：最常见的访问控制失效

第 5 章讲逻辑漏洞时提到过 IDOR（不安全的直接对象引用），这里讲全：越权访问分两种。水平越权：普通用户 A 改个参数就看到了普通用户 B 的数据（/order?id=124 看别人的订单）。垂直越权：普通用户改个参数就干了管理员才能干的事（把请求里的 role=user 改成 role=admin，或者直接访问 /admin/delete）。防御的原则只有一条，模块六第 10 章讲过：每次访问资源，都要在服务器端检查“这个身份有没有权做这件事”——不是“登录了没有”，而是“这个资源是不是他的、这个操作是不是他的角色能做的”。检查要放在服务器端、放在每个接口上，不能只靠前端隐藏按钮：前端不显示“删除”按钮，攻击者直接发请求照样能删。

还有一句要补上，关于密码。认证再强，也架不住弱密码。按 NIST SP 800-63B Rev.4 的最新要求：单独使用的密码至少 15 位，不要再迷信“大小写+数字+符号拼出来的 8 位复杂密码”——长度比复杂度重要得多；同时要强制检查泄露密码库，用户设的密码如果出现在已泄露的密码里，必须拒绝。配合模块六第 9 章的多因素认证，才是完整的认证防线。

老师经验：测认证，最忌讳“只测登录框”。登录框只是认证的入口，真正的检查点散落在每一个接口上：改个 ID 看别人的数据、改个角色参数提权、把 JWT 的算法改成 none、把过期令牌再发一次。我养成了一个习惯：拿到一个网站，先不急着找注入，而是把所有接口按“要不要登录、要什么角色、返回了谁的数据”列一张表，再逐个改参数试。越权漏洞就是这样被“数”出来的。还有一句：测 JWT 时，先把令牌贴到解码工具里看一眼载荷——很多令牌里明明白白写着 "role": "user"，改成 admin 再发回去，服务器如果只看载荷不验签名，你就进去了。这个测试五分钟就能做完，却经常有大发现。

动手做

1. 只在自己的虚拟机里：找一个 JWT 解码工具（或用 Python 的 base64 解开），看一个靶场发给你的令牌：头部算法是什么、载荷里写了哪些字段、有没有敏感信息；再试着把算法改成 none、把角色改成 admin 发回去，记录服务器的反应。
2. 在 DVWA 或自己写的测试网站里做越权测试：登录普通账号，把订单 ID、用户 ID 逐个改成别人的，看能不能看到别人的数据；再试着直接访问管理员接口，记录哪一次被拦住了、哪一次没拦住。
3. 检查 CORS 配置：用 curl 看一个本地站点的响应头，记下 Access-Control-Allow-Origin 的值，判断它是白名单还是 *，有没有同时允许凭证。
4. 按 NIST SP 800-63B Rev.4 写三条密码策略：单独使用的密码至少 15 位、强制查泄露密码库、配合多因素认证，并说明为什么“长度比复杂度重要”。

避坑

只在自己的靶场里测认证和越权：改真实网站的参数去看别人的数据、提权，是越界行为；别把 JWT 载荷当秘密：它只是编码，任何人都能解开，敏感信息绝不能放进去；别接受 alg=none：服务器必须只认白名单里的算法；CORS 的 Origin 绝不能是 * 又带凭证；权限检查必须在服务器端每个接口上做，前端隐藏按钮不算防御；密码按 NIST SP 800-63B Rev.4：单独使用至少 15 位，强制查泄露密码库，别再迷信短而复杂的密码。

会话与认证这一章讲完，Web 漏洞的“攻击面”基本讲全了：从注入、脚本、伪造请求，到上传、逻辑、XXE、反序列化，再到今天的认证与越权。下一章我们换一个角色：从“打一个点”变成“看一张网”——第 8 章：信息收集与扫描进阶，讲讲动手之前的信息收集：Nmap、漏洞扫描和 OSINT。记住本章反复出现的原则：检查要放在服务器端做——这个原则在扫描和利用阶段同样适用。

本课小结
  • JWT 由头部、载荷、签名三部分组成；载荷只是编码不是加密，签名才是防篡改的关键；常见攻击有 alg=none、弱密钥爆破、密钥混淆。
  • CORS 配错（Origin 为 * 又允许凭证）等于让任意网站带着用户 Cookie 读数据；Origin 必须写白名单。
  • CSP 是服务器给浏览器立的规矩，从严配置，少用 unsafe-inline；它是防 XSS 的重要纵深防线。
  • 越权分水平（看别人的数据）和垂直（干管理员的活）；防御是每次访问都在服务器端检查“身份 × 资源 × 操作”。
  • 密码按 NIST SP 800-63B Rev.4：单独使用的密码至少 15 位，强制查泄露密码库，长度比复杂度重要，配合多因素认证。
