模块四第 23 章：调试与测试深入：单元测试与调试器

编程基础2026-11-25 · 模块四

写了 22 章代码，你一定已经体会过：代码第一次跑起来就全对的概率，约等于零。bug 是编程的常态，不是例外——区别只在于，你是靠“盯着屏幕猜”找 bug，还是靠一套方法找 bug。这一章讲两个基本功：调试器（出了 bug 怎么找）和单元测试（怎么证明 bug 真的修好了、以后不再犯）。动手做是给第 15 章的密码检查器写单元测试——你前面写过的工具，第一次有了自己的“体检表”。

调试器：让程序停下来，慢慢看

新手找 bug 的常用办法是到处加 print：这里打印一个变量、那里打印一句话，跑一遍看输出、改一处再跑一遍。这办法能用，但效率低：程序跑起来是一瞬间的事，你想看的是“某一行执行时，变量到底是多少”，print 只能事后告诉你。调试器（debugger）是更直接的办法：它能让程序在你指定的地方停下来，然后你慢慢看——看每个变量的值、看调用栈、看程序下一步要去哪。

调试器的四个基本动作：断点（breakpoint）——在某一行设个点，程序跑到这里就停住；单步执行（step over / step into）——一次走一行，step over 是“这一行直接跑完”，step into 是“这一行里有函数调用，就钻进去看”；查看变量（watch）——停住的时候看每个变量当前的值，重点看“和你想的不一样的那一个”；调用栈（call stack）——看程序是怎么一层一层调到这里来的：是哪个函数调了哪个函数，参数传进来时是什么。

Python 自带的调试器是 pdb：python3 -m pdb 程序.py 启动，或者在代码里插一行 breakpoint()，跑到那里自动停住。VS Code 里更直观：在行号左边点一下设断点，按 F5 跑起来，程序停住后鼠标悬停就能看变量值。调试器的使用习惯就一句话：先猜一个“最可能出错的地方”，在它前面设断点，停住之后看变量——变量会告诉你猜得对不对。猜错了就换个地方再猜，猜的次数越少，说明你对程序的理解越深。

单元测试：给每个函数写一张体检表

调试器解决“这个 bug 在哪”，单元测试解决“这个 bug 以后还会不会回来”。单元测试（unit test）就是给一个函数写一小段“检查程序”：喂它几个输入，断言（assert）输出必须是什么。Python 标准库的 unittest 和第三方的 pytest 都是现成框架，pytest 的写法最简洁：写一个 test_xxx.py 文件，里面是 def test_xxx(): assert check("abc") == ... 这样的函数，跑 pytest 就全测一遍，哪个断言不过、哪一行红了，一目了然。

写测试要抓住三类输入：正常情况（强密码应该得高分）、边界情况（正好 15 位的密码、空字符串、只有一个字符）、异常情况（None、数字、超长输入）。边界最容易出 bug：>= 15 写成 > 15，正好 15 位的密码就被错判了——这种错肉眼很难发现，测试一跑就现形。安全工具的测试还要多一类：攻击者视角的输入——带引号的、带 <script> 的、超长的、含换行的，都要测一遍，确保程序是“拒绝或安全处理”，而不是崩溃或执行了不该执行的东西。

测试覆盖率与回归测试：测了多少，有没有倒退

测试覆盖率（coverage）回答“你的代码有多少被测试跑到过”：跑一遍测试，再用 coverage 工具统计每一行有没有被执行到。覆盖率 100% 不等于没有 bug——测试可以跑到某一行，但不断言它的输出对不对；但覆盖率低一定有问题：没跑到的代码，就是没人验证过的代码。对初学者来说，覆盖率的目标不是 100%，而是“核心逻辑都测到了”：判断逻辑的每个分支、每个边界，都至少有一个测试走到。

回归测试（regression test）是测试的长期价值：每修一个 bug，先写一个能复现这个 bug 的测试（跑它，确认它现在是红的），修好之后再跑（确认它变绿了），然后把这个测试留下来——以后每次改代码都跑一遍全部测试，只要它再变红，就说明这个 bug 又回来了。没有回归测试的修 bug 是“这次修好了，下次还可能犯”；有了回归测试，每修一个 bug，程序就永久地变强一点。第 24 章的工具集验收，靠的就是这一套测试。

还有一个习惯要养成：测试要快、要独立、要能反复跑。测试里不要连真实网络、不要读真实数据库、不要依赖“现在是几点”——依赖外部的东西，测试就会时好时坏，最后没人愿意跑。需要外部数据时，用假数据代替（这叫 mock）：本地文件、写死的返回值，都行。测试跑得越快，你越愿意跑；越愿意跑，bug 就越早被抓住。

老师经验：我带过的团队里，调试水平的分水岭不是“会不会用调试器”，而是“会不会先想再动手”。新手看到报错就开始改代码：改一行、跑一遍、再改一行，像在黑暗里扔飞镖。老手是先停下来读报错：报错说的是哪一行、哪个变量、什么类型，再设一个断点验证猜想——十次里有八次，bug 在动手之前就已经定位了。还有一个血泪教训：有一次我们修好一个登录 bug，没写回归测试，三个月后另一个人改了同一块代码，bug 原样回来，用户又投诉了一轮。从那以后团队立了规矩：修 bug 必须先写复现测试，测试红了才能开始修，绿了才能算修完。这个规矩看起来慢，实际上省了最多的时间——因为返工才是最贵的。最后一条：测试不是“写给别人看的”，是写给三个月后的你自己看的。那时候你早就忘了这段代码为什么这么写，测试就是唯一能告诉你“它本来应该干什么”的东西。

动手做

1. 给第 15 章的密码检查器写单元测试：新建 test_password_checker.py，用 pytest 写至少 8 个测试——强密码得高分、弱密码得低分、正好 15 位的边界、空字符串、纯数字密码、含常见弱口令（比如 password、123456）的输入、超长输入、None 输入。跑一遍 pytest，看是全绿还是有红的；有红的，先别急着改测试，看看是不是检查器本身有 bug。
2. 故意制造一个 bug 再抓它：把密码检查器里的 >= 15 改成 > 15，跑一遍测试，看哪个测试变红了——体会“测试是怎么抓住边界 bug 的”；再把代码改回去，确认测试重新变绿。
3. 用调试器抓一个真 bug：在虚拟机里用 VS Code 打开密码检查器，在评分逻辑前设断点，喂一个你预期得高分、实际得了低分的密码，单步走一遍，看是哪个变量先和你想的不一样；再用 pdb（python3 -m pdb）重复一次，熟悉两种调试方式。
4. 测一遍覆盖率：给密码检查器跑 pytest --cov（先 pip install pytest-cov），看覆盖率是多少、哪几行没被测到，再补两个测试把核心分支盖满——目标不是 100%，是“核心逻辑的每个分支都有测试走到”。

避坑

别到处加 print 找 bug：print 只能事后看输出，调试器能让程序停下来慢慢看；别看到报错就立刻改代码：先读报错、猜一个位置、设断点验证，猜的次数越少说明理解越深；别只测正常输入：边界、异常、攻击者视角的输入才是 bug 的藏身之处；别追求 100% 覆盖率：覆盖率低一定有问题，但 100% 不等于没 bug，核心逻辑测到才是目标；别修了 bug 不留测试：没有回归测试，同一个 bug 迟早会回来；别让测试依赖真实网络和真实数据库：测试要快、要独立、要能反复跑，外部数据用假数据代替。

调试和测试是工程师每天吃饭的家伙，也是下一章结课实战的验收标准。下一章 第 24 章：动手：综合实战——写一个自己的安全小工具集，把端口扫描器、密码检查器、日志分析器整合成一个带命令行菜单的工具集，再加 README、检查清单和验收标准。回头看第 12 章的软件工程：调试、测试、代码评审那时是概念，这一章是亲手做了一遍——概念只有落到手上，才算真的会了。

本课小结
  • 调试器让程序在断点处停下来：单步执行一次走一行，查看变量看当前的值，调用栈看程序是怎么一层层调到这里的——先猜位置、设断点、看变量验证猜想。
  • 单元测试是给每个函数写体检表：喂输入、断言输出，pytest 写起来最简洁；三类输入都要测——正常、边界、异常，再加攻击者视角的输入。
  • 测试覆盖率回答“多少代码被测试跑到过”：目标不是 100%，是核心逻辑的每个分支都有测试走到；跑到不等于断言对了。
  • 回归测试是修 bug 的正确收尾：先写复现测试（红的），修好（变绿），留下来——以后每次改代码都跑一遍，bug 回来了立刻现形。
  • 测试要快、独立、能反复跑：不连真实网络、不读真实数据库，外部数据用假数据代替，跑得越快越愿意跑。
