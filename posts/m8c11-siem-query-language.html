模块八第 11 章：SIEM 查询语言：KQL/SPL 与检测规则编写

安全运营与应急响应2026-11-25 · 模块八

第 2 章我们认识了 SIEM：它把各处的日志收在一起，变成可以查的东西。但“可以查”和“会查”是两回事——一台服务器一天就能产生几十万条日志，靠眼睛翻是翻不完的。这一章学查日志的语言：KQL 和 SPL。它们是安全分析师的“筛子”，学会它们，你就能从几十万条日志里，一句话筛出你想要的那几条；学完还会把一句查询变成一条检测规则，让 SIEM 以后自动帮你盯着。

先把概念说清：SIEM 像一个大仓库，日志是仓库里的货；查询语言就是你跟仓库管理员说话的方式。“把昨天所有登录失败的记录找出来”是一句人话，翻译成查询语言，SIEM 才能执行。KQL 是微软 Sentinel 用的语言，SPL 是 Splunk 用的语言。它们长得不一样，但思路完全一样：先指定查哪张表（哪类日志），再一层一层加条件，最后决定输出什么样子。学会一种，另一种一看就懂。

KQL 入门：像搭积木一样查日志

KQL 的写法像搭积木，用竖线 | 把一步步操作串起来，读起来就是一句流水账。举个例子，查“昨天登录失败的记录”：

SigninLogs | where TimeGenerated > ago(1d) | where ResultType != 0 | project TimeGenerated, UserPrincipalName, IPAddress

拆开读：第一段 SigninLogs 是说查登录日志这张表；第二段 where TimeGenerated > ago(1d) 是说只要最近一天的；第三段 where ResultType != 0 是说只要结果不是成功的（在微软的登录日志里，结果类型 0 代表成功，其他数字代表各种失败原因）；最后一段 project 是说输出时只要时间、用户名、IP 这三列，别的不用给我看。每一竖线都是一次筛选，越往后结果越少、越准。

KQL 里最常用的几个操作要记住：where 是过滤（只要满足条件的行）；project 是选列（只要这几列）；count 是计数；summarize 是汇总，比如 summarize count() by UserPrincipalName 就是“按用户名分组数一数，每个人失败了多少次”。这一个操作最能帮你发现暴力破解：正常人输错密码两三次就停了，一个账号一小时失败上百次，基本就是有人在猜密码——这正是第 5 章模拟入侵里要复原的那种痕迹。

SPL 入门：Splunk 的说法

SPL 的思路和 KQL 一模一样，只是写法不同。同样是“查登录失败”，SPL 大概长这样：

index=windows EventCode=4625 | stats count by Account_Name, Source_Network_Address | sort -count

拆开读：index=windows 是说查 Windows 日志这个索引；EventCode=4625 是说只要事件编号 4625——这是 Windows 里“登录失败”的编号，第 13 章会专门讲这些编号；stats count by ... 是说按账号和来源 IP 分组计数；sort -count 是说按次数从多到少排。排在最前面的，就是失败次数最多的账号和 IP，第一眼就能看到可疑目标。

两种语言对照着记效果最好：KQL 的 where 对应 SPL 的搜索条件，KQL 的 summarize 对应 SPL 的 stats，KQL 的 project 对应 SPL 的 fields。工作中用哪个，取决于公司买了哪家的 SIEM；但面试和自学时，两种都见过、都能读懂，比只会一种要强得多。

从查询到检测规则

一条查询是你手动跑一次；一条检测规则是让 SIEM 定时替你跑，跑出结果就自动产生告警。一条完整的规则有四部分：查询（查什么）、触发条件（查出多少算有问题，比如 10 分钟内失败 10 次以上）、严重程度（高/中/低）、动作（产生告警、发通知、交给谁处理）。写规则之前，先问自己三个问题：第一，我要抓的攻击手法是什么？（对照第 3 章的 ATT&CK 手法，比如暴力破解是 T1110）；第二，正常情况下这件事会发生吗？（管理员偶尔输错密码很正常，所以阈值不能设成 2 次）；第三，响了之后，值班的人知道该怎么办吗？（不知道怎么办的规则，等于没写）。

举一个完整的例子——检测“暴力破解登录”。KQL 写法：先按账号和 IP 分组，数最近 10 分钟的失败次数，超过 10 次就告警：

SigninLogs | where TimeGenerated > ago(10m) | where ResultType != 0 | summarize FailCount = count() by UserPrincipalName, IPAddress | where FailCount >= 10

这个规则的好处是思路透明：任何人读一遍都知道它在抓什么。它的弱点也要知道：如果攻击者慢慢猜（每小时只试几次），就躲过了阈值；如果攻击者换很多 IP 来猜，分组计数也会被冲淡。所以真实的 SOC 里，一条规则很少单打独斗，往往是几条规则互相配合——这正是第 18 章检测工程要深入讲的事。

写查询的三个习惯

第一个习惯是先小后大：先写一句最简单的查询，确认它能跑出结果，再一层一层往上加条件。一次性写十层管道，出错了都不知道是哪一层的问题。第二个习惯是先数数再下结论：查到可疑结果，先数一数它出现了多少次、涉及多少账号——一次是偶然，一百次是模式。第三个习惯是把查询存下来：每条查出过真问题的查询，都值得存进你的“查询手册”，下次遇到类似告警，直接拿出来改两个条件就能用。很多资深分析师的效率，一半来自他们攒了多年的查询手册。

还有一个习惯是给查询起名字。SIEM 里存了上百条查询，没有名字的查询，过三个月连自己都认不出来。起名字有个简单的格式：手法 + 数据源 + 目的，比如“暴力破解-登录日志-10分钟失败10次”。名字起好了，别人接手你的工作时，一眼就知道这条查询是干什么的。

老师经验：我刚做 SOC 分析师的时候，写的第一条规则一晚上响了 400 多条告警，值班的同事第二天差点把规则删了。问题出在我把阈值设成了“失败 3 次就告警”——正常人早上刚睡醒输错三次密码太常见了。后来我学到一个土办法：写规则之前，先用查询在过去 7 天的数据上跑一遍，看看它每天会响多少次；如果一天超过 20 次，先别急着上线，把阈值调高、把条件收紧，或者加一个白名单（比如排除掉公司内部的扫描器 IP）。还有一条：规则上线后第一个星期，每天都要回头看它产生的告警，问一句“这条是真的吗”；连续三天全是误报的规则，要么改，要么关。告警的信用是攒出来的——响得准，大家才会在它响的时候真的去看。

动手做

1. 只在你自己的虚拟机或实验环境里：打开 Windows 事件查看器，找几条真实的登录失败记录（事件 4625），抄下它的时间、账号、来源 IP，理解每一条日志长什么样。
2. 在纸上（或记事本里）写出三句查询：查“今天所有登录失败”、查“失败次数最多的前 5 个账号”、查“某个 IP 一小时内失败了多少次”，先用中文写思路，再试着翻译成 KQL 或 SPL 的样子。
3. 把第 2 步里“失败次数最多的账号”那句查询，改写成一条完整的检测规则：写出查询、触发条件（几分钟内失败几次）、严重程度和告警后第一步该做什么。
4. 用过去 7 天的思路检验你的规则：如果它每天会响 100 次，说明阈值太松了，把条件收紧一档再算一遍，直到一天响的次数降到个位数。

避坑

别一上来就写复杂查询：先从一句 where 开始，跑通了再加一层，十层查询一次写出来，出错了都不知道哪一层错了；别把阈值拍脑袋定下来：先在历史数据上跑一遍，看它每天会响多少次再上线；别只学一种语言就以为够了：KQL 和 SPL 思路相通，工作中遇到另一种要能读懂；别把检测规则当成一劳永逸：攻击手法会变、业务会变，规则要定期回顾，长期没响过的规则也要检查是不是已经失效了；别在真实生产系统上练手：所有查询练习都在自己的虚拟机或实验日志上做。

上一章第 10 章我们学了怎么写一份事件报告——报告里写的“证据”，很多就是从这样的查询里筛出来的。这一章你学会了筛日志的语言和写检测规则的方法。下一章第 12 章我们换一个角度：规则响了、告警来了，SOC 里的人是怎么分轻重缓急、按剧本一步步处理的——查询是手艺，工作流是让一群人配合起来的办法。

本课小结
  • KQL 和 SPL 思路相同：先指定查哪类日志，再一层层加条件，最后决定输出什么样子。
  • KQL 常用操作：where 过滤、project 选列、summarize 分组汇总；SPL 对应的是搜索条件、stats、fields。
  • 按账号分组数登录失败次数，是发现暴力破解最直接的办法；Windows 登录失败的事件编号是 4625。
  • 一条检测规则 = 查询 + 触发条件 + 严重程度 + 动作；写规则前先在历史数据上跑一遍，看每天会响多少次。
  • 好规则的标准是响得准：误报太多，告警的信用就没了；规则上线后要定期回顾，长期不响的也要检查。
