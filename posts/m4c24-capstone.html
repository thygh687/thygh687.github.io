模块四第 24 章：动手：综合实战——写一个自己的安全小工具集

编程基础2026-11-25 · 模块四

24 章学完了，你手里已经有三个能干活的工具：第 14 章的端口扫描器、第 15 章的密码检查器、第 16 章的日志分析器。但它们还是三个散落的脚本：各跑各的、各写各的日志、结果各存各的地方。这一章是模块四的结课实战：把三个工具整合成一个带命令行菜单的小工具集，加上 README 和使用说明，再给出检查清单和验收标准。做完这一章，你交出来的不再是“三个练手脚本”，而是一个别人拿到就能用的小工具——这是从“会写代码”到“会做工具”的分水岭。

先想清楚：工具集长什么样

动手写代码之前，先定结构。一个命令行工具集通常长这样：一个入口程序（比如 sectools.py），启动后打印菜单：1 端口扫描、2 密码检查、3 日志分析、0 退出；用户输数字进子功能，跑完回到菜单。每个子功能是一个独立的模块文件（scanner.py、checker.py、analyzer.py），入口只负责“显示菜单、读选择、调模块”，不实现具体功能——这就是第 6 章讲的模块化：改扫描器的逻辑，不用碰菜单的代码；加第四个工具，只要再写一个模块、菜单里加一行。

三个模块之间还要约法三章：统一的日志格式（时间、模块名、级别、消息，一行一条，写进同一个日志文件）；统一的结果存放（第 20 章的 SQLite：扫描结果、检查结果、分析结果都进同一张库，表分开，查的时候能跨表对照）；统一的错误处理（出错了不崩溃、不悄悄吞掉，按第 21 章的规矩：给用户一句话、给日志记全部）。约法三章定下来，工具集才像一个整体，而不是三个脚本拼在一起。

整合三步：搬、接、验

第一步，搬：把三个工具的函数原样搬进各自的模块文件。搬的时候只做一件事：把“写死在代码里”的东西抽出来——目标地址、端口范围、密码规则、日志文件路径，全部改成参数或配置文件里的值。扫描器原来写死扫 127.0.0.1，改成从菜单读目标（只允许 127.0.0.1 和你虚拟机的内网地址，别的地址直接拒绝——工具集的第一条安全规矩：它只能碰你自己的机器）；密码检查器的 15 位规则来自 NIST SP 800-63B Rev.4，写成常量放在文件开头，改规则只改一行。

第二步，接：把三个模块接到统一的底座上。结果入库：每个模块跑完，把结果写进 SQLite（扫描结果进 ports 表、检查结果进 passwords 表、分析结果进 alerts 表，建表和写入的逻辑放在一个共用的 db.py 里，三个模块都调它）；日志统一：一个共用的 log.py，三个模块都用它记日志，格式一致；错误处理统一：每个模块的入口包一层 try/except，出错了记日志、回菜单，不让整个工具集崩掉。

第三步，验：按第 23 章的办法给工具集写测试。每个模块至少 5 个单元测试（正常、边界、异常各有），再加 3 个“端到端”测试：启动工具集、选 1、扫本地、回菜单；选 2、检查几个密码；选 3、分析一小段日志——全程只碰本地数据。测试全绿，才算整合完成；有红的，先修模块、再跑测试，红变绿之前不算完。

README 和使用说明：工具的一半是文档

工具集写完了，还差一半：README。一个别人拿到就能用的 README 至少要有五节：这是什么（三个工具是干什么的）、怎么运行（Python 版本、要装的库、启动命令）、怎么用（菜单上每个选项是干什么的、输什么、会出什么结果）、结果存在哪（数据库文件在哪、日志文件在哪、怎么查）、安全说明（只能扫自己的机器、只能分析自己的日志、不要拿去碰别人的系统）。写 README 的时候，假装读者是你三个月后的自己：那时候你早就忘了启动命令和数据库文件名，README 是唯一能救你的东西。

使用说明里还要写清边界：这个工具集是学习用的，不是生产工具——它没有做身份认证、没有做访问控制、不能扛住恶意输入的狂轰滥炸。边界写清楚，既是对使用者负责，也是对你自己负责：一个工具的作者，要对它的能力边界诚实。

检查清单与验收标准

整合完成之前，对着下面这张清单逐项打勾。检查清单（做的时候用）：

□ 三个模块都搬进了独立文件，入口只负责菜单；□ 目标地址、端口范围、规则阈值都改成了参数，没有写死的值；□ 结果都进了 SQLite，三个模块共用同一个库文件；□ 日志格式统一，三个模块记在同一个日志文件里；□ 每个模块的入口都有 try/except，出错回菜单、不崩溃；□ 扫描目标做了白名单限制：只允许 127.0.0.1 和本机虚拟机地址；□ README 五节写全，安全说明里写清“只能碰自己的机器”；□ 每个模块至少 5 个单元测试，全绿；□ 3 个端到端测试全绿。

验收标准（交卷的时候用）：启动工具集，菜单正常显示；选 1，输入 127.0.0.1 和端口范围 20–100，扫描完成，结果能在数据库里查到，日志里有记录；选 2，输入几个强弱不一的密码，评分结果符合 15 位长度优先的规则（单独使用的密码至少 15 位）；选 3，输入一段含可疑登录失败的日志，分析结果正确标出可疑 IP；选 0，正常退出；故意输一个非法菜单选项（比如 9），程序不崩溃、提示重新输入；故意输一个非法目标（比如一个公网 IP），程序拒绝执行并记日志；全部测试 pytest 一次跑过，全绿。以上任何一项不过，都不算完成——回清单里找对应的那一项，修好再验。

老师经验：我见过太多“能跑但没人敢用”的内部工具：作者离职了，没人知道启动命令；数据库文件不知道在哪；出了错不知道看哪个日志。工具和脚本的区别，不在功能多少，而在“别人能不能接手”：菜单清不清楚、结果存在哪、出错了看什么、边界是什么——这四件事写明白了，工具才算完成。还有一条现场经验：整合的时候最容易犯的错是“顺手改功能”——搬扫描器的时候觉得“顺便把超时也改了”，搬日志分析器的时候“顺便把规则也调了”，最后三个模块全变了，测试全红，不知道是谁改坏的。整合期间只搬、不改：先让三个旧功能在新结构里原样跑起来，全绿了，再一个一个改。先搭架子、再装修，顺序反了就要返工。

动手做

1. 在虚拟机里新建一个文件夹 sectools，把第 14 章的端口扫描器、第 15 章的密码检查器、第 16 章的日志分析器分别搬成 scanner.py、checker.py、analyzer.py，再写一个 sectools.py 做菜单入口：菜单 1/2/3/0，选 0 退出，其他选项调对应模块、跑完回菜单。
2. 接上统一底座：写一个共用的 db.py（建表 + 写入，三个模块的结果都进同一个 SQLite 文件）和一个共用的 log.py（统一格式的日志），三个模块改成调它们；再给每个模块入口包一层 try/except，出错记日志、回菜单。
3. 给扫描器加白名单：只允许 127.0.0.1 和你虚拟机的内网地址，其他目标直接拒绝并记日志——用一个真实的公网 IP 试一次，确认它真的被拒绝了（只试拒绝逻辑，不要真的去扫）。
4. 写 README 和验收：按本章的五节写好 README，再按验收标准逐项跑一遍：菜单、扫描、检查、分析、退出、非法选项、非法目标、pytest 全绿——全部通过才算模块四毕业。

避坑

别在整合的时候顺手改功能：先让旧功能在新结构里原样跑起来、全绿了，再一个一个改；别把目标地址写死：扫描目标必须是参数，还要有白名单限制，只能碰自己的机器；别让一个模块的错误拖垮整个工具集：每个模块入口都要有 try/except，出错回菜单；别忘了 README：没有文档的工具，三个月后连你自己都不会用；别把“测试全绿”当成可有可无：验收标准里任何一项不过，都不算完成；别拿工具集去碰别人的系统：它只能扫自己的虚拟机、分析自己的日志，真实网络和他人系统是红线。

模块四到这里就结束了：从第 1 章“编程是怎么回事”到这一章的工具集，你已经从一行代码走到了一个能用的小工具。下一站是模块四小结：从一行代码到一个小工具，把 24 章串起来，再看一遍你现在能做什么。回头看模块三第 5 章的 TCP 和端口：那时你是在“用手查”端口，现在你写的工具能“用代码查”——模块三和模块四就是这样接上的。编程不是换一个话题，是把前面“用手查”的本事，变成“用代码查”的本事。

本课小结
  • 工具集的结构：一个入口只管菜单，三个模块各管一个功能，共用一个 SQLite 结果库和一份统一格式的日志；加新工具只要再写一个模块、菜单加一行。
  • 整合分三步：搬（函数原样搬进模块，写死的值改成参数）、接（接上统一的结果库、日志和错误处理）、验（单元测试 + 端到端测试，全绿才算完成）。
  • README 是工具的一半：是什么、怎么运行、怎么用、结果存在哪、安全说明，五节缺一不可，边界要写清楚。
  • 验收标准是硬的：菜单、扫描、检查、分析、退出、非法选项、非法目标、pytest 全绿，任何一项不过都不算完成。
  • 工具集只能碰自己的机器：扫描目标白名单限制在 127.0.0.1 和本机虚拟机地址，真实网络和他人系统是红线。
