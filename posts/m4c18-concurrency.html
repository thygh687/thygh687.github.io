模块四第 18 章：并发编程：线程与锁

编程基础2026-11-25 · 模块四

上一章的内存错误讲的是“一个人写坏了自己的地盘”，这一章的问题是“几个人同时写同一块地盘”。第 14 章的端口扫描器一次扫一个端口：扫 1000 个端口要等 1000 次，每次等对方回音都要花时间——大部分时间程序其实什么都没干，只是在等。如果让 20 条线同时去扫，速度能快 20 倍。这就是并发：一个程序里同时做几件事。并发能让程序快起来，也能让 bug 变得神出鬼没：两个线程同时改同一个数字，结果每次运行都不一样。这一章讲线程、竞态条件、锁、死锁和线程池，动手做是在虚拟机里写一个只连本地服务的多线程下载器雏形。

进程和线程：先分清这两个词

模块二讲过，进程是操作系统分配资源的单位：每个进程有自己独立的内存，进程之间互不干扰。线程是进程里面的执行线：同一个进程里的线程共享同一块内存，共享同一份数据。打个比方：进程是一间独立的办公室，线程是办公室里的几个人——各干各的活，但共用同一张桌子、同一台打印机。浏览器就是典型：一个进程里，一个线程在画页面，一个线程在下载图片，一个线程在响应你的点击。

共享内存是线程的优点，也是麻烦的根源：几个人共用一张桌子，效率高，但两个人同时去拿同一支笔，就会抢起来。线程共享数据让协作变得容易，也让“谁先改、谁后改”成了一个必须认真对待的问题。

竞态条件：结果取决于谁跑得快

竞态条件（race condition）是并发里最常见的 bug：程序的正确结果取决于两个线程谁先跑到某一步，而谁先跑到是不确定的。看一个最简单的例子：一个全局计数器 count = 0，两个线程各把它加 1 一万次，你以为最后是 20000，对吗？不一定。

“加 1”在机器层面是三步：读出 count 的值、加 1、写回去。如果线程 A 读出 5，正要写回 6 的时候，线程 B 也读出了 5，算出 6 写回去——两个线程各加了一次，计数器却只涨了 1。这一次“加 1”就丢了。跑一万次下来，丢多少次全看两个线程交错的时机，每次运行的结果都不一样。这种 bug 最折磨人：测试时跑十次都对，上线第一天就错，因为测试时机器空闲、线程交错少，生产环境一忙就撞上了。

竞态条件不只是计数器的问题：安全领域里它有个更危险的版本叫 TOCTOU（检查时间与使用时间不一致）：程序先检查“这个文件能不能写”，检查通过了，真正去写的时候，文件已经被换成了另一个——检查和使用的中间那一瞬间，就是攻击者的窗口。第 21 章讲安全编码时还会回到这个例子。

锁：一次只让一个人进房间

对付竞态条件的标准办法是锁（lock，也叫互斥锁 mutex）：把“读—算—写”这三步包进一个临界区，规定同一时间只能有一个线程在里面。线程进临界区之前先拿锁，拿到了才能进，拿不到就等着；出临界区时把锁还回去。就像卫生间的门锁：里面有人，门就是锁着的，其他人只能等。

Python 里锁的写法很直观：threading.Lock() 建一把锁，with lock: 包住要保护的代码。关键是“保护的范围要刚好”：锁住的代码越少，并发效果越好——只锁住真正需要保护的那几行，不要把整个函数都锁起来；但也不能锁少了：读和写必须在同一把锁里，否则等于没锁。还有一个容易踩的坑：锁是手动还的，中间抛了异常、提前 return 了，锁没还上，其他线程就永远等下去——所以要用 with 这种自动还锁的写法，别手写拿锁还锁。

锁之外还有别的同步工具：信号量（semaphore）限制“同时最多几个人进”，读写锁区分“读可以一起读、写必须一个人写”，队列（queue）让线程之间用“传纸条”代替“共用一张桌子”——生产者把任务放进队列，消费者从队列里取，谁也不用直接碰对方的数据。能用队列就别用裸锁：队列是 Python 标准库里线程安全的现成工具，出错的面小得多。

死锁：两个人互相等对方先松手

锁用多了会长出一种新 bug：死锁（deadlock）。线程 A 拿着锁 1，等锁 2；线程 B 拿着锁 2，等锁 1——两个人各捏着对方要的东西，谁也不松手，程序就永远卡住了。死锁有四个成立条件：互斥（锁一次只能一个人拿）、占有并等待（拿着一个还要另一个）、不可抢占（别人不能强行夺走）、循环等待（A 等 B，B 等 A）。破掉其中任何一个，死锁就不成立。

工程上最实用的防死锁办法只有一条：所有线程拿锁的顺序必须一致。规定“要拿两把锁时，永远先拿编号小的，再拿编号大的”，循环等待就永远形不成。还有两条辅助办法：拿锁时设超时，超时拿不到就放手重试，别死等；锁的数量越少越好，能一把锁解决的就别用两把。死锁一旦发生，程序不报错、不崩溃，只是“不动了”——这比崩溃更难查，因为日志里什么都没有，只剩两个互相等待的线程。

线程池：别每来一个任务就开一个线程

线程不是免费的：每个线程都要占一块栈内存，操作系统创建和销毁线程也要花时间。扫描 1000 个端口就开 1000 个线程，机器先被线程自己拖垮了。正确做法是线程池：预先开好固定数量的线程（比如 20 个），任务排进队列，线程从队列里一个一个取任务做，做完接着取下一个。任务再多，线程数也不涨，资源消耗是可控的。

Python 标准库里现成的线程池是 concurrent.futures.ThreadPoolExecutor：建一个 max_workers=20 的池子，把任务 submit 进去，等结果就行。还有一个新手常问的问题：Python 有全局解释器锁（GIL），多线程是不是假的并行？答案是分情况：GIL 只限制“同时只能有一个线程在执行 Python 字节码”，但线程在等网络回音、等磁盘读写的时候会主动放开 GIL——所以网络、文件这类“等得多、算得少”的任务，多线程是真提速；纯计算（比如算一百万个哈希）多线程提速有限，那是多进程的活。端口扫描、下载、爬日志这类安全工具，恰恰都是“等得多”的任务，所以线程池是它们的标配。

老师经验：有一次客户的日志采集程序每天凌晨会“丢”几百条日志，重启就好，过几天又丢。查了磁盘、查了网络，最后发现是两个线程共用一个没加锁的写入计数器：计数器一乱，程序按错误的偏移量写文件，后面的日志就盖掉了前面的。最气人的是这个 bug 只在凌晨业务高峰才出现，白天怎么测都测不出来。从那以后我给团队立了条规矩：凡是两个线程都能碰到的数据，必须在代码里一眼看出来它被哪把锁保护着——看不出来的，就当它没保护。还有一条：并发 bug 不要靠“多跑几次看看”来验证，跑一百次都对不代表没问题，时序一变就翻车；验证并发的办法是把临界区想清楚，或者用 ThreadSanitizer 这类工具去扫，而不是碰运气。

动手做

1. 在虚拟机里写一个计数器实验：两个线程各把一个全局变量加 1 一万次，不加锁跑五次，记下每次的结果是不是 20000；再给“读—算—写”加上 threading.Lock 跑五次，对比结果——亲眼看到竞态条件，才能真正记住它。
2. 在虚拟机里用 python3 -m http.server 8000 起一个本地服务，再写一个多线程下载器雏形：用线程池（ThreadPoolExecutor，20 个线程）同时去取本地服务上的几个文件，只连 127.0.0.1，统计总耗时，再和单线程版对比——只在本地做，绝不去碰真实网站。
3. 把第 2 步的下载器改成“下载到一半会出错”的版本：让本地服务随机返回 500 错误，练习用队列把失败的任务收集起来重试一次，并保证重试时不会有两个线程同时写同一个文件（用锁保护写文件那几行）。
4. 在虚拟机里故意写一段死锁：两个线程按相反的顺序拿两把锁，跑起来看程序是不是卡住了；再用 Ctrl+C 打断它，然后改成统一拿锁顺序，确认程序能正常跑完。记住死锁长什么样：不报错、不崩溃，只是“不动了”。

避坑

别以为“我的程序只有两个线程，不会出竞态条件”：两个线程就够了，一个读一个写就能撞上；别用共享变量在线程之间传数据，优先用队列，队列是线程安全的，裸变量不是；别在持有一把锁的时候去拿另一把锁，除非你已经想清楚了拿锁顺序——拿锁顺序不一致就是死锁的温床；别每来一个任务就开一个线程，任务一多先想线程池；别拿“多跑几次都对了”当作并发正确的证据：竞态条件和死锁都是时序相关的，测试环境越空闲越测不出来；别把纯计算任务交给多线程提速：Python 的 GIL 会让它们排队跑，算得多、等得少的活要交给多进程。

并发让第 14 章的端口扫描器能一次扫几百个端口，也让第 19 章要讲的 HTTP 客户端能同时发很多请求——先把锁和线程池这两个工具握在手里，下一章 第 19 章：用代码调 HTTP 与 API，我们写程序去访问网络。回头看第 17 章的内存错误：多线程共享内存时，一个线程写坏了内存，另一个线程读到的就是坏数据——内存错误和并发错误经常结伴出现，查 bug 时要两个方向一起想。

本课小结
  • 线程是进程里的执行线：同一进程的线程共享内存，所以协作容易，但“谁先改数据”成了必须管的问题。
  • 竞态条件是“加 1”这类操作其实是读、算、写三步，两个线程交错执行会丢掉一次更新，结果每次运行都不一样。
  • 锁把临界区一次只交给一个线程：保护范围要刚好，用 with 自动还锁，拿多把锁时所有线程的顺序必须一致，否则会死锁。
  • 线程池预先开固定数量的线程、任务排队取用，避免每任务开一个线程把机器拖垮；Python 的 ThreadPoolExecutor 是现成工具。
  • Python 的 GIL 只限制同时执行 Python 字节码：等网络、等磁盘的任务多线程真提速，纯计算任务要交给多进程。
