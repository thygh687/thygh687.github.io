模块二第 15 章：分段与地址转换 —— 分页之前，先有分段

操作系统2026-11-25 · 模块二

第 7 章讲虚拟内存和分页时，留了一个问题没展开：程序看到的地址是怎么变成真正的物理地址的？分页是一种答案，但它不是历史上唯一的答案。在分页成为主流之前，操作系统用的是分段。理解分段，再回头看分页，你会明白分页到底好在哪、又丢了什么。更重要的是，分段的思想并没有死透——它换了个样子，活在今天的 x86-64 处理器和操作系统里。

先说分段要解决的原始问题。早期的程序是直接用物理地址的：程序说“我要地址 1000 的数据”，CPU 就去物理内存 1000 号位置拿。两个程序同时跑，地址就打架了——A 程序的数据放在 1000，B 程序也想放 1000，谁让谁？更糟的是，一个程序写错地址，能把另一个程序的数据甚至操作系统自己的数据覆盖掉。分段的想法是：别让程序直接说物理地址，让它说“第几段里的第几个位置”，操作系统在中间做一次翻译。

基址 + 界限：最简单的分段

最简单的分段方案叫“基址 + 界限”。每个程序分到一段连续的物理内存，操作系统记下两个数：基址（base，这段内存从哪个物理地址开始）和界限（limit，这段内存有多长）。程序访问地址时，说的是段内的偏移（offset，从段开头数第几个字节）；CPU 把基址加上偏移，得到真正的物理地址，同时检查偏移有没有超过界限——超过了，就触发越界错误，程序被拦下来。

举个例子：程序 A 的基址是 10000，界限是 5000。程序想访问段内偏移 200 的位置，CPU 算出物理地址 10200，在界限内，放行；程序想访问偏移 8000，超过界限 5000，CPU 拒绝，报错。这两个数一加一查，就同时解决了两个问题：不同程序的地址不再打架（它们的基址不同，段内偏移相同，翻译出来的物理地址也不同），一个程序也写不到别人的地盘上（界限检查把它拦住了）。

基址 + 界限的方案简单，但有个毛病：每个程序只能占一段连续内存。程序的代码、数据、栈挤在同一段里，没法分开保护——代码段应该只读，数据段应该可读写，栈应该可读写但不可执行，挤在一起就没法区别对待。而且程序想要扩大一点内存，操作系统得在物理内存里找一块更大的连续空地，把整个程序搬过去，搬家成本很高。

分段表：一个程序，多段内存

改进的办法是：一个程序可以有多个段——代码段、数据段、栈段，各自一段，每段有自己的基址、界限和权限。操作系统给每个程序维护一张段表（segment table），每一行（段描述符）记录一段的基址、界限和权限（可读？可写？可执行？）。程序访问内存时，地址不再是一个数，而是两个数：段号 + 段内偏移。CPU 先拿段号去段表里查到这一段的基址和界限，再像前面一样做加法和越界检查，还要多查一项权限：想往只读的代码段里写数据？权限检查直接拒绝。

分段的好处这时就显出来了：第一，保护可以按段来，代码只读、数据读写、栈不可执行，各管各的；第二，段与段之间可以共享：两个程序共用同一段代码（比如共用的库函数），段表里让它们的代码段指向同一块物理内存就行，省内存；第三，段的大小可以按需长大，数据段不够了，操作系统在后面接一块空地就行，不用整个程序搬家。

分段的毛病也在这里：段是大小不一的，物理内存用久了会产生“外部碎片”——空闲内存被切成一块块小的、互不相连的碎片，合起来够大，但没有一块连续的能放下一个新段。操作系统要么花时间搬动已有的段来整理碎片，要么眼睁睁看着内存够用却放不下东西。这个毛病，分页正好能治——这是 第 7 章讲分页时埋下的伏笔。

分段和分页，各解决什么问题

把分段和分页放在一起对比，是本章最重要的一张表。分段是按程序的逻辑来切：代码是一段、数据是一段、栈是一段，段的大小不一，边界对程序员有意义。分页是按固定大小来切：不管程序逻辑，一律切成 4KB 一页，页的大小固定，边界对程序员没有意义。

分段解决的是“逻辑组织和保护”：按功能分段，权限按段给，共享按段来。分页解决的是“物理内存管理”：固定大小的页，随便往哪个空闲页框里放，不产生外部碎片，换入换出也以页为单位，简单高效。一个管“程序长什么样”，一个管“内存怎么分”，关注点根本不在一个层面上。所以现代操作系统的做法是两个都要：先用分段的思想做逻辑划分和保护，再用分页做物理内存管理——只不过在 x86-64 上，分段的那一步被大大简化了。

现代系统为什么以分页为主，分段还剩什么

现代系统以分页为主，原因有三。第一，分页没有外部碎片，内存利用率高；第二，固定大小的页让换入换出、内存映射变得简单，虚拟内存、内存映射文件、写时复制这些机制都是建立在分页之上的；第三，分页的地址翻译可以用多级页表加 TLB（快表）加速，硬件支持成熟。分段的段表查找和变长段管理，在硬件实现上要麻烦得多。

但分段并没有完全消失。在 x86-64（64 位模式）下，处理器仍然有段寄存器（CS、DS、SS、FS、GS），只是大多数段的基址被强制当作 0，段的界限检查也被关掉了——这叫“平坦内存模型”，程序看到的地址直接就是线性地址，交给分页去翻译。例外是 FS 和 GS 这两个段寄存器：它们的基址仍然有效，操作系统用它们来存“每个 CPU / 每个线程自己的数据”——Windows 用 GS 存线程环境块（TEB），Linux 用 FS 存线程本地存储（TLS）。你在调试器里看到 fs:0 或 gs:0 这样的地址，背后就是分段留下的最后一点遗产。

从安全角度看，分段留下的教训比它的实现更重要。第一，地址翻译是隔离的第一道墙：程序看到的地址和真正的物理地址之间必须隔着一层翻译，否则程序就能直接碰别人的内存——这正是 第 7 章讲的页表隔离的同一个道理。第二，权限要按“最小的单位”给：分段按段给权限，分页按页给权限（可读、可写、可执行分开），现代的“数据段不可执行”（NX 位）就是分页层面上的权限思想——栈上的数据不能当代码执行，挡住了很大一类缓冲区溢出攻击。第三，共享要显式：分段时代共享一段内存要在段表里明说，分页时代共享也要在页表里明说——凡是“能共享”的地方，都是安全审计要重点看的地方。

老师经验：排错时，分段的思想比它的历史更实用。有一次一个程序一启动就崩，报错是访问违规（access violation），地址看起来很小，像是 0x00000000 附近。我第一反应不是去看代码，而是问：这个地址是哪个段的？——空指针解引用读的是地址 0 附近，那是操作系统故意留出来的“谁都不许碰”的区域，分页的权限把它标成不可访问，所以一碰就崩。如果地址是栈附近的大地址，可能是栈溢出；如果是堆的地址，可能是野指针。同一个“访问违规”，地址落在哪个范围，指向完全不同的原因。还有一次看恶意软件样本，它用 FS 段找线程环境块，再从里面找进程环境块、找加载的模块列表——这是 Windows 恶意软件的经典起手式，不用调任何系统调用，光靠 FS 段就能摸清自己身在何处。分段在今天的实战里，就是 FS 和 GS 这两个寄存器。

动手做

全部在虚拟机里做，不用写代码，用现成的工具看。1. 在虚拟机里的 Linux 上跑 cat /proc/self/maps，看一个进程的内存分段：每一行是一段映射，有起始地址、权限（rwxp 里的 r、w、x 分别是可读、可写、可执行）、映射的是哪个文件。找出哪一段是可执行的代码（r-xp）、哪一段是可读写的数据（rw-p）、哪一段是栈（[stack]）。2. 跑 readelf -l /bin/ls | grep -A2 LOAD，看一个可执行文件的程序头：它在磁盘上就已经分好了段（LOAD 段），每一行标着在内存里的权限。对比第 1 步的 maps，看看磁盘上的分段和运行时的分段是怎么对应的。3. 在 Windows 虚拟机或自己的 Windows 上，用任务管理器看一个进程的内存占用，再想一想：如果没有分页和分段，两个程序同时想用地址 1000 会发生什么？把答案写下来。

避坑

别把“段”和“页”混为一谈：段是按逻辑切、大小不一，页是按固定大小切、一般 4KB；别以为分段已经死了：FS/GS 段寄存器在 64 位系统里还活着，线程本地存储就靠它；别以为地址翻译只是为了“多用内存”：它首先是隔离和保护，没有翻译就没有进程隔离；看 /proc/self/maps 时别被地址吓到：每个进程看到的都是自己的虚拟地址，两个进程的 0x7f 开头的地址指向的根本不是同一块物理内存。

地址翻译的两大方案到这里就齐了：分段管逻辑，分页管物理。下一章回到 CPU 时间：第 16 章：调度深入讲多级反馈队列和 Linux 的完全公平调度——CPU 时间到底怎么分才公平。

本课小结
  • 分段让程序说“段号 + 段内偏移”，CPU 查段表得到基址和界限，加法得到物理地址，越界就拒绝——同时解决地址冲突和越界保护。
  • 段表每行记录一段的基址、界限和权限：代码段只读、数据段读写、栈不可执行，保护可以按段来，共享也可以按段来。
  • 分段按逻辑切、大小不一，会产生外部碎片；分页按固定大小切，没有外部碎片，现代系统以分页为主。
  • x86-64 下分段基本被平坦化，但 FS/GS 段寄存器还活着：Windows 用 GS 存线程环境块，Linux 用 FS 存线程本地存储。
  • 地址翻译首先是隔离：程序看不到真实物理地址，才碰不到别人的内存；权限按最小单位给，是 NX 保护的思想源头。
