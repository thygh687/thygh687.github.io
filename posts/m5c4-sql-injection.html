模块五第 4 章：SQL 注入是怎么发生的

数据库与密码学2026-11-25 · 模块五

这是模块五里最重要的一章，也是整个安全学习里最经典的一课：SQL 注入。它常年排在 OWASP Top 10（最危险的 Web 风险清单）的前列，二十多年过去了，依然有网站因此丢数据。好消息是，它的原理一点都不难——难的是很多程序员写了十年代码也没真正想明白。这一章只讲原理和防御，不讲攻击手法；实战利用在模块七第 2 章，而且只在合法靶场里做。

一切的起点：字符串拼接

想象一个登录页面：用户输入用户名和密码，程序要去数据库里查“有没有这么一个人”。很多初学者会这样写代码（这里用伪代码，道理都一样）：

sql = "SELECT * FROM users WHERE name = '" + 用户输入的用户名 + "' AND password = '" + 用户输入的密码 + "'";

这行代码做的是字符串拼接：把程序写好的 SQL 模板和用户输入的东西用加号粘在一起，拼成一条完整的 SQL，再交给数据库执行。正常输入时没问题：用户名填 alice，密码填 123456，拼出来的 SQL 是：

SELECT * FROM users WHERE name = 'alice' AND password = '123456';

数据库一查，有这个人，登录成功。问题出在：程序根本分不清，哪些字符是它自己写的模板，哪些是用户输入的——拼在一起之后，全都是一条 SQL 语句。

一个单引号，怎么“逃出”查询

第 1 章讲过：字符串要用单引号包起来，单引号在 SQL 里有特殊含义——它标志着“字符串从这里开始、到那里结束”。攻击者利用的正是这一点。如果用户名输入的不是 alice，而是 ' OR '1'='1，拼出来的 SQL 就变成了：

SELECT * FROM users WHERE name = '' OR '1'='1' AND password = '随便什么';

看发生了什么：输入里的第一个单引号，提前“关上”了用户名字符串；接着的 OR '1'='1' 变成了一个新的条件——而 '1'='1' 永远是真的。整条 WHERE 条件被改写了：原来要同时满足“名字对、密码对”，现在只要满足“名字是空，或者 1 等于 1”——后半句永远为真，整条条件永远为真，数据库就把 users 表的第一行（常常是管理员账号）当作“登录成功”返回了。密码那一栏填什么，已经不重要了。

这就是注入这个名字的由来：用户输入的不是数据，而是被注入进了 SQL 语句、改变了语句结构的代码。数据库分不清数据和指令，因为程序在拼接的时候就把它们混在了一起。

注入的三种常见形态

第一种，绕过登录。上面那个例子就是：不用知道密码，用一个永远为真的条件骗过登录检查。这是最经典的形态，也是很多演示里第一个展示的。

第二种，偷看不该看的数据。如果查询条件被改写成永远为真，返回的就不是一行，而可能是全表——用户的邮箱、手机号、密码哈希，全都可能被一次查出来。更进一步，攻击者还能用 UNION 把另一个表的查询结果“拼”进同一次返回里。

第三种，破坏和越权。如果程序用的数据库账号权限够大，注入的语句甚至可以不只是 SELECT——可以改数据、删表，乃至在数据库服务器上执行命令。这就是为什么“最小权限”在防御里和预编译语句一样重要：就算注入发生了，权限不够大，破坏也被关在笼子里。

这三种形态的根子是同一个：用户输入被当成了 SQL 代码的一部分。记住这一句，防御的思路就全通了。

防御：预编译语句 + 最小权限

预编译语句（Prepared Statement）是正解，而且是唯一应该依靠的正解。做法是：先把带占位符的 SQL 模板发给数据库——SELECT * FROM users WHERE name = ? AND password = ?，数据库先把这条语句的结构定下来、编译好；然后再把用户输入作为纯数据单独发过去，填进问号的位置。这时输入里的单引号再多，也只会被当作一个普通字符串里的字符，永远改不了语句的结构。结构和数据分了家，注入就无从下手。

注意一个常见的误区：靠“过滤掉单引号、分号这些危险字符”来防注入，是靠不住的。攻击者总有绕过黑名单的办法（比如用编码、大小写、双写），而过滤一旦漏掉一个，整个防御就垮了。正确的心态是：不靠过滤，靠结构——预编译语句从机制上让注入不可能发生。

最小权限是第二道防线：连接数据库的账号，只给它完成工作所必需的最小权限。网站前台的查询账号只需要 SELECT，就别给它 DELETE、DROP，更别给它数据库管理员权限。这样即使某处漏了注入，攻击者能造成的破坏也被限制在最小范围。数据库的加固（最小权限、备份、预编译语句的落地检查）会在模块五第 11 章系统讲。

老师经验：我审计过的系统里，SQL 注入出现最多的地方不是登录框，而是搜索框和排序参数——程序员给登录加了预编译，却忘了搜索框里那句 ORDER BY + 用户输入。还有一次，一个系统所有查询都用了预编译，唯独后台一个导出功能是拼接的，结果被从后台打穿了。所以审计时我有一条笨办法：全局搜索代码里所有拼 SQL 的地方，一个一个过，拼 SQL 的地方就是注入可能住的地方。另外提醒一句：不要在面试或聊天里炫耀“某某网站有注入”——发现漏洞的正确做法是按负责任披露的流程报告给对方，拿真实网站练手是违法的，实验只在自己的虚拟机和合法靶场里做。

动手做

只在自己的虚拟机、自己的练习库上做，绝不在任何真实网站、真实网络上试：
1. 在虚拟机里，用 Python 写一段演示代码：先用字符串拼接拼一条查询，把 ' OR '1'='1 当用户名输进去，打印出拼好的 SQL 语句，亲眼看它长什么样——只打印，不执行到别人的库上，执行的库是你自己的 vuln_lab.db；
2. 在自己的 vuln_lab.db 上执行这条被注入的查询，对比正常查询返回几行、注入的查询返回几行，理解“条件被改写成永远为真”是什么意思；
3. 把同一段代码改成预编译写法（Python 的 sqlite3 用 cursor.execute("SELECT * FROM vulns WHERE name = ?", (user_input,))），再输一次同样的注入字符串，看这回返回几行——答案是 0 行，因为它被当成了一个普通的字符串去匹配；
4. 检查一遍：你的练习库连接用的是什么权限？SQLite 是文件级权限，想想换成 MySQL 时该怎么建一个只有 SELECT 权限的账号。
做完这四步，你就同时理解了注入是怎么发生的、为什么预编译能防住它。实战利用（在合法靶场 DVWA 里从发现到利用再到写报告）是模块七第 2 章的事。

避坑

别靠过滤危险字符防注入，要靠预编译语句；别把数据库账号设成管理员权限连网站，查询账号只给 SELECT；别在任何真实网站上试注入，哪怕“只是看一下”——那是违法行为；别以为登录框加了预编译就安全了，搜索、排序、导出这些角落最容易漏；密码不要明文存数据库里，密码该怎么存是模块五第 9 章的主题。

注入讲的是“数据被当成代码”的危险。接下来换一个方向：密码学里，数学是怎么让“就算被人看到也看不懂”成为可能的——第 5 章：密码学需要的数学：模运算、素数与椭圆曲线。

本课小结
  • 注入的根子是字符串拼接：用户输入和 SQL 模板粘在一起，数据库分不清哪是数据、哪是指令。
  • 一个单引号能提前关上字符串，OR '1'='1' 这样的永远为真条件可以改写整条 WHERE，绕过登录或拖出全表数据。
  • 三种常见形态：绕过登录、偷看不该看的数据、破坏和越权；根子都是同一个。
  • 防御靠预编译语句（结构和数据分家）加最小权限（就算漏了，破坏也被关在笼子里）；别靠过滤黑名单。
  • 注入只在自己的虚拟机练习库和合法靶场里研究，绝不在真实网站上试；实战在模块七第 2 章。
