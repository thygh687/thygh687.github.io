模块四第 21 章：安全编码深入：输入验证、输出编码与密钥管理

编程基础2026-11-25 · 模块四

前面几章的安全习惯是零散的：第 17 章说“写之前先问够不够长”，第 19 章说“密钥别写死在代码里”，第 20 章说“SQL 里掺了用户输入就必须参数化”。这一章把它们收成一套完整的规矩：安全编码。核心只有一句话——永远不信任输入。用户输入、文件内容、网络回来的数据、数据库里读出来的旧数据，凡是程序自己没生成的，一律先当成可疑的，验过、编过、管好之后再用。这一章没有新语言要学，只有六条规矩：每条规矩背后，都有真实出过事的教训。

第一条：永远不信任输入

“输入”不只是键盘上敲的字：网址里的参数、上传的文件、API 返回的 JSON、日志文件里的一行、甚至数据库里存了三个月的一条旧记录，都是输入。攻击者控制输入的办法多得是：表单里填、网址里改、文件里藏、接口里塞。程序员最常见的错觉是“这个输入是内部系统传来的，肯定是干净的”——内部系统的数据，最初也是从某个用户手里来的。

不信任输入，不是不用输入，而是用之前先过三道关：验格式（是不是我想要的样子）、验范围（是不是在我允许的区间里）、验长度（是不是在我准备好的大小内）。三道关都过了，才放行；任何一道不过，就拒绝、记日志、给用户一个礼貌的错误提示。拒绝输入不是程序“不好用”，是程序“分得清能吃什么、不能吃什么”。

第二条：白名单验证，别用黑名单

验证有两种思路：黑名单是“列出不许出现的东西，其他都放行”，白名单是“列出只许出现的东西，其他都拦下”。黑名单的问题在于，你永远列不完坏东西：拦了 <script>，攻击者可以用大小写混写、双写、编码绕过，拦得越多、漏得越多。白名单反过来：只允许你明确知道是好的东西，比如“用户名只能是字母、数字和下划线，长度 3 到 20 位”，其他一律拒绝——攻击者再怎么变花样，也变不出白名单以外的东西。

白名单的落地办法很具体：数字就转成数字再验范围（年龄 0 到 150，端口 1 到 65535，数量不能是负数）；枚举值就对照一张固定的表（状态只能是 open、closed、filtered 三个词之一，其他都拒绝）；字符串就用第 8 章的正则表达式限定字符集和长度。记住一个判断标准：你的验证规则能不能一句话说清“什么样的是合法的”？能，就是白名单；只能说清“什么样的是非法的”，就是黑名单，该换了。

第三条：输出编码——数据去哪，就按哪的规矩编码

输入验证管的是“进来的东西”，输出编码管的是“出去的东西”。同一份数据，放到不同的地方要按不同的规矩处理：显示在网页上，< 要变成 &lt;，否则浏览器会把它当成标签执行——这就是跨站脚本攻击（XSS）的根子；拼进 SQL 里，要用第 20 章的参数化查询，而不是拼接；写进日志里，要去掉换行符，否则攻击者能用假的换行伪造日志行；传给命令行时，要当成参数传，而不是拼成命令字符串，否则就是命令注入。

关键是理解“编码不是加密，也不是过滤”：编码是把数据翻译成目标场合能安全接受的样子——浏览器看到 &lt;script&gt; 只会显示成文字，不会执行它。原则是：编码要在输出的那一刻、按输出的目的地来做，不要在输入时就把数据改得面目全非——同一份用户名既要显示在网页上、又要写进数据库，输入时改掉它，两个地方都会错；输出时各编各的，才是对的。

第四条：密钥不要写死在代码里

第 19 章调 API 时已经立过这条规矩，这里讲全：密钥、密码、令牌这类凭证，绝不能出现在代码里、配置文件里随手提交的版本里、日志里、报错信息里。正确的做法分三层：开发时放环境变量（os.environ.get("API_KEY")），部署时用系统或云平台的密钥管理服务，代码里只读不存。更进一步：密钥要能轮换（定期换一把新的，旧的作废），要分权限（只读的密钥不要给成可写的），要设有效期。

为什么这条规矩这么严？因为代码会流动：传到 GitHub、拷到 U 盘、发给同事、备份到云盘——任何一个环节，写死的密钥都会跟着走。真实世界里，大量数据泄露的起点就是有人把带密钥的代码推到了公开仓库，机器人几分钟内就能扫到。检查方法很简单：写完代码，全文搜一遍 password、secret、api_key 这些词，看看有没有真实的凭证躺在里面；再检查一遍 .gitignore，确认放凭证的配置文件真的没被提交。

第五条：错误信息别泄露信息

程序出错时，给用户看什么、给日志记什么，是两回事。给用户看的错误信息要模糊：登录失败就说“用户名或密码错误”，不要说“这个用户名不存在”——后者等于告诉攻击者“这个用户名可以排除，换下一个试”；查不到数据就说“没有找到”，不要把数据库的报错原文、表名、SQL 语句甩给用户看。给日志记的则要详细：时间、哪个接口、什么输入、哪一行抛的异常，全记下来——日志是给自己人看的，越详细越好查。

这条规矩的另一面是异常处理：第 7 章的 try/except 不是“让程序不崩溃”的装饰，而是“出错时按我安排的方式收场”的工具。异常要捕获在离出错最近、也最知道该怎么办的那一层，捕获之后要么恢复、要么干净地失败，绝不能悄悄吞掉（空的 except 是最坏的写法：程序错了，你还不知道）。

第六条：依赖要及时更新

你的程序不是孤岛：requests、sqlite3 之外的每一个第三方库，都是别人写的代码。你用的库有漏洞，你的程序就有漏洞——而且是你看不见的漏洞。规矩有三条：只用还在维护的库（看它的最近更新时间、issue 有没有人理）；固定版本号并记录下来（requirements.txt），升级之前先在虚拟机里测一遍；定期检查已知漏洞（pip audit 这类工具能扫出你用的库有哪些已公开的 CVE）。第 12 章讲软件工程时提过“代码评审”，依赖更新就是评审的一部分：每次评审都问一句“我们用的库有没有新版本、有没有已知漏洞”。

老师经验：我职业生涯里见过损失最大的安全事故，根子不是什么高深的攻击，而是一条写在代码里的数据库密码。那个密码跟着代码进了版本库，又跟着版本库进了外包团队的电脑，最后出现在一个公开的代码片段分享网站上——数据库被拖走的时候，没有任何“攻击”的痕迹，因为用的就是合法的密码。从那以后，我审代码的第一步永远是全文搜凭证，第二步是看错误信息会不会把表名和 SQL 吐给用户。还有一条血泪经验：报错信息要分“给用户看的”和“给日志记的”——有一次我们把数据库报错原文直接显示在页面上，攻击者靠着报错里泄露的表名和字段名，半小时就拼出了一条能用的注入语句。错误信息不是越详细越好，详细要留给日志，留给用户的一句话就够了：出错了，请稍后再试。

动手做

1. 在虚拟机里给第 15 章的密码检查器加一道白名单验证：密码只允许规定的字符集，用户名只许字母、数字和下划线、长度 3 到 20 位，不合规的输入直接拒绝并记日志——把“验证在用之前做”落到自己写过的代码上。
2. 写一个输出编码小实验：准备一段含 <script> 的输入，分别用“原样输出到网页”和“用 html.escape 编码后输出”两种方式生成 HTML 文件，在浏览器里打开对比——亲眼看到编码前后一个会被当成代码、一个只显示成文字。
3. 做一次凭证大扫除：在虚拟机里建一个小项目，把 API 密钥放进环境变量（Windows 用 setx、Linux 用 export），代码里只用 os.environ 去读；再用全文搜索检查项目里有没有真实凭证躺在代码或配置文件里，并写好 .gitignore 保证放凭证的文件不会被提交。
4. 给自己的三个小工具（端口扫描器、密码检查器、日志分析器）各做一次“依赖检查”：列出它们用的第三方库，查一遍有没有已知漏洞、有没有新版本，写一张一页纸的清单：库名、当前版本、最新版本、有没有已知漏洞。

避坑

别用黑名单做验证：你列不完坏东西，白名单才是正道；别在输入时就把数据改得面目全非：编码要在输出的那一刻、按输出的目的地来做；别把密钥写进代码、日志和报错里：凭证只放环境变量或密钥管理服务，代码里只读不存；别把详细的报错甩给用户：给用户一句话，给日志记全部；别悄悄吞掉异常：空的 except 等于把眼睛闭上，程序错了你还不知道；别以为“内部工具就不用讲安全”：内部工具的数据最初也是从用户手里来的，拼接字符串的查询在内部一样会出事；别装了库就再也不管：依赖要定期检查更新和已知漏洞。

六条规矩收齐了，安全编码就有了骨架。下一章换换脑子：第 22 章：图算法与动态规划——图怎么表示网络、怎么找最短路，动态规划又是怎么把大问题切成小问题的。回头看第 17 章的内存错误和第 20 章的参数化查询：它们和这一章的六条规矩其实是同一件事——在“东西进来”和“东西出去”的每一个口子上，都先问一句“这样安全吗”。

本课小结
  • 安全编码的核心是永远不信任输入：用户输入、文件内容、网络数据、数据库旧记录，用之前都要先验格式、验范围、验长度。
  • 验证要选白名单：只放行明确知道是好的东西；黑名单永远列不完坏东西，漏掉一个，攻击就进来了。
  • 输出编码要在输出的那一刻、按目的地来做：上网页要转义、进数据库要用参数化、进日志要去掉换行、进命令行要当参数传。
  • 密钥绝不写死在代码、日志和报错里：放环境变量或密钥管理服务，代码只读不存，还要能轮换、分权限、设有效期。
  • 错误信息分两套：给用户一句话、给日志记全部；依赖要定期检查更新和已知漏洞，内部工具也要按外部标准写。
