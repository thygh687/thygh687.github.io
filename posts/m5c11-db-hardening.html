模块五第 11 章：数据库加固：最小权限、备份与预编译语句

数据库与密码学2026-11-25 · 模块五

数据库是大多数系统的心脏：用户、订单、密码哈希（第 9 章讲过怎么存）、证书记录，全在里面。攻击者一旦进了数据库，拿到的往往不是一条数据，而是整个业务。这一章讲数据库加固的六件事：最小权限、预编译语句、输入验证、备份与恢复演练、审计日志、打补丁。它们没有一件是高深技术，全是“把基本功做到位”——而真实世界里的数据泄露，十有八九就是基本功没做到位。

先把这一章和前面的注入分开：SQL 注入“是怎么发生的”，原理在模块五第 4 章，实战利用在模块七；这一章讲的是防法——作为开发者和运维，你怎么让注入即使发生了也造不成大伤害，以及怎么让它根本发生不了。防和攻是同一枚硬币的两面，学防的时候心里要装着攻的样子。

最小权限：应用账号只给需要的权限

最小权限原则的意思是：每个账号、每个程序，只能拿到完成工作所必需的最小权限，多一点都不给。数据库里最常见的违规，就是应用用一个“上帝账号”连数据库：能读、能写、能删表、能建用户，什么都能干。网站的正常功能其实只需要对某几张表做增删改查，删表、改结构这种事，应用一辈子都不需要做。把权限收紧之后，即使攻击者通过注入拿到了这个账号，他也只能在授权的范围内折腾，删不了表、看不到别的库、建不了后门账号。

具体怎么做：给应用单独建一个数据库账号，只授权它要用的那几张表、那几种操作（SELECT、INSERT、UPDATE、DELETE），不要给 DROP、ALTER、CREATE USER、GRANT 这些管理权限；不同应用用不同账号，不要共用一个；开发、测试、生产用不同的账号和不同的密码；数据库管理员账号只给人用，不给程序用，密码要进密码管理器，不要写在配置文件里——配置文件里的密码要用专门的密钥管理服务或环境变量注入，第 10 章讲密钥管理的思路在这里同样适用。定期复查一次权限：这个账号上次用 DROP 是什么时候？从来没用过就收回来。

预编译语句：让数据永远只是数据

SQL 注入的根源，是程序把用户输入直接拼进 SQL 语句里。比如登录查询写成 SELECT * FROM users WHERE name = '" + 用户名 + "' AND password = '" + 密码 + "'"，攻击者输入 ' OR '1'='1，拼出来的语句就变了样，条件永远为真，不用密码就登进去了。防法的核心就一句话：不要拼接 SQL，让数据库把“指令”和“数据”分开处理。实现它的标准办法就是预编译语句（prepared statement / 参数化查询）。

预编译语句的做法是：先把 SQL 的结构发给数据库编译好，留出占位符，比如 SELECT * FROM users WHERE name = ? AND password = ?，数据库先把这条语句的结构定下来；然后再把用户输入当作纯粹的参数值传过去。数据库保证：参数永远只会被当成数据，不会被当成 SQL 指令来执行。攻击者输入 ' OR '1'='1，数据库只会去找用户名真的是 ' OR '1'='1 的用户——找不到，登录失败。结构先定、数据后填，注入就没有了下手的地方。

几乎所有主流语言和框架都有现成的参数化查询：Python 的 sqlite3 / psycopg2 用 ? 或 %s 占位符，Java 用 PreparedStatement，PHP 用 PDO，ORM（比如 Django、SQLAlchemy）默认就是参数化的。用 ORM 不等于自动安全——原生 SQL 查询、动态拼接表名和排序字段的地方，仍然可能中招；表名、列名、排序方向不能用占位符，这些地方要用白名单校验。记住：凡是 SQL 语句里出现用户输入的地方，先问一句“这是不是参数化查询”。

输入验证：第一道关，但别只靠它

输入验证是让不合法的输入根本进不了系统：年龄必须是数字、邮箱必须像邮箱、用户名只允许字母数字下划线、长度有上限。验证的原则是白名单优先：只允许已知的合法格式，而不是去拉黑已知的坏字符——黑名单永远列不完，攻击者总能找到你没想到的写法。验证要在服务端做：浏览器里的 JavaScript 校验只是为了用户体验好，攻击者可以直接绕过浏览器发请求，服务端的校验才是真正的一道关。

但输入验证不能代替预编译语句。原因很简单：合法输入里也可能含有 SQL 特殊字符——一个姓 O'Brien 的用户，名字里就带单引号；一篇正常的文章里也可能有分号和引号。靠“过滤掉危险字符”来防注入，会误伤正常用户，而且总有绕过的办法。正确的分工是：输入验证管“格式对不对”，预编译语句管“注入进不进得来”，两道关各司其职。

备份与恢复演练：备份不是存了就行，要能恢复才算数

备份的意义不是“存了一份”，而是“出事时能恢复”。勒索软件加密了数据库、管理员误删了一张表、硬盘坏了——这时候能救命的只有备份，而且是能恢复的备份。备份要做到四点：定期（按业务定，全量加增量，比如每天全量、每小时增量）；异地（备份不要只放在同一台服务器上，服务器被加密了备份也一起没了，至少一份放别的机器或对象存储）；加密（备份里有全量数据，泄露了和数据库泄露一样严重，备份文件要加密、访问权限要收紧）；演练（定期真的恢复一次，验证备份文件没损坏、恢复流程跑得通、恢复出来的数据是对的）。

“演练”两个字要特别强调：我见过太多团队备份跑了三年，从来没恢复过，真出事那天才发现备份脚本三个月前就报错了，或者备份文件损坏了一半。恢复演练要像消防演习一样定期做：每季度至少一次，在测试环境里把备份恢复出来，对一遍关键数据，计时——恢复要多久，直接决定了业务能停多久（RTO）和能丢多少数据（RPO），这两个指标要和业务方提前商量好、写下来，而不是出事了再争论。

审计日志与打补丁：出事时能查，平时别留洞

审计日志记的是“谁、什么时候、对数据库干了什么”：登录成功失败、建表删表、批量导出、大额修改。日志要记到数据库服务器之外的地方（比如集中日志系统），否则攻击者删库的同时顺手把日志也删了，就死无对证了。日志还要有人看：定期 review 异常——凌晨三点的大批量 SELECT、平时从不用的账号突然登录、一次导出几十万行，这些都是要报警的信号。日志本身也要保护：只追加不修改、定期归档、访问权限收紧。

打补丁是最枯燥、也最容易被拖延的一项：数据库软件、操作系统、驱动，出了安全补丁要及时评估、及时打。很多泄露事件利用的都是几个月前就公开的已知漏洞。补丁流程要固定下来：测试环境先验证、生产环境分批打、打完验证业务正常、留回滚方案。补丁打得慢，本质上是把已知的大门敞开着等人来推。

老师经验：我做过一次事故复盘，起因是开发图方便，应用账号给了 DROP 权限，注入进来的人一条 DROP TABLE 就把订单表删了，备份还是三个月前的——那次之后我养成了一个习惯：新系统上线前，我只查三张表——应用账号的授权清单、备份的最后一次成功恢复演练日期、最近一次补丁时间。还有一次，客户的数据库被拖库，查日志发现攻击者三个月前就用注入拿到了只读权限，慢慢把数据一点点导出去，而日志根本没人看。日志没人看，等于没记。我的建议是：每周花 15 分钟，只看三类日志——失败登录、批量导出、管理操作，15 分钟能挡住一大半的“潜伏式”攻击。

动手做

只在虚拟机里做，用自己建的测试数据库。1. 在虚拟机里装 SQLite（Python 自带），建一张测试表 users，插几条测试数据。2. 先写一段有注入漏洞的代码：用字符串拼接做登录查询，输入 ' OR '1'='1，看它是不是不用密码就登进去了——只在你自己的测试库里试。3. 把同一段查询改成预编译语句（Python sqlite3 的 ? 占位符），再输入同样的注入字符串，看它是不是被当成普通用户名处理、登录失败。4. 给测试库建两个账号（概念上用 SQLite 的文件权限模拟）：一个只有读权限，一个什么都能干，对比注入成功后两者能造成的破坏有什么不同。5. 做一次备份恢复演练：把测试库文件复制一份当备份，删掉原表，再用备份恢复回来，计时并验证数据对不对。6. 打开数据库的日志（SQLite 可以用 Python 记录每次查询），看一看你的注入尝试在日志里长什么样。

避坑

别给应用账号上帝权限——只给它要用的表和操作，DROP、ALTER、建用户这些管理权限一律不给；别拼接 SQL——所有带用户输入的查询都用预编译语句或 ORM 的参数化查询，表名、列名用白名单；别只在浏览器里做输入验证——服务端校验才是真的一道关，而且验证不能代替预编译语句；别只备份不演练——没恢复过的备份等于没有备份，备份还要异地、加密；别把审计日志存在数据库本机——出事时日志会被一起删掉，日志要集中存放、有人定期看；别拖补丁——已知漏洞不修，等于把门敞开；所有实验只用自己的虚拟机和测试库，别碰任何真实系统和真实数据。

数据库加固做完，下一章要换个工具练手：第 12 章用 OpenSSL 亲手生成密钥对、自签名证书、加密解密文件——把前面几章讲的加密、证书、密钥，变成你手里真正跑过的命令。回头看第 10 章的密钥管理：私钥文件权限、备份加密，这些要求在 OpenSSL 实验里马上就能练到。

本课小结
  • 最小权限：应用账号只给要用的表和操作，不给 DROP、ALTER、建用户等管理权限；不同应用、不同环境用不同账号。
  • 预编译语句是防 SQL 注入的标准办法：先编译 SQL 结构、再把用户输入当纯数据传，参数永远不会被当成指令执行。
  • 输入验证用白名单、在服务端做，但它管格式、不能代替预编译语句；姓 O'Brien 这种合法输入里也有单引号。
  • 备份要定期、异地、加密，更要定期做恢复演练：没恢复过的备份等于没有备份，恢复耗时和可丢数据量要提前定好。
  • 审计日志要记到数据库之外、有人定期看失败登录、批量导出和管理操作；数据库和系统的安全补丁要及时打。
